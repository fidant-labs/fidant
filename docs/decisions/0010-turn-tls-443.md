# 0010: TURN over TLS on 443, routed by SNI on the app box

- Status: Accepted
- Date: 2026-11-24
- Linear: SIG-93

## Context

- 0007 put coturn on the app box with no TLS listener. The relay answers only on UDP and TCP 3478.
- Many office and guest networks let out only TCP 443. A browser there can't reach the relay, so a pair that needs it fails.
- Caddy already holds 443 on the box, for the app at fidant.se and the five redirect names. The box has one static IPv4 address, so only one process can listen on 443.
- 0006's per-address caps key on the client address that Caddy puts in X-Forwarded-For, trusted only from loopback. Anything put in front of Caddy must keep that address.
- 0008's refused sends keep only the `stun:` URLs. Removing a `stun:` URL would leave them without STUN.
- `parseIceServers` accepts at most 4 URLs, and 0007 already uses all 4 when the box has IPv6.
- Ubuntu 24.04 ships Caddy 2.6 and coturn 4.6.1. Caddy reads the PROXY protocol in its standard build only from 2.7.
- We tested the setup below on Ubuntu 24.04 in containers, and Chrome against coturn with TLS, before writing this record.

## Options considered

| Option                                                                  | For                                                                                                                    | Against                                                                                                                                                  |
| ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A: HAProxy on 443 routes by SNI, without decrypting, to Caddy or coturn | One box. Neither TLS stream is decrypted by a third process. Caddy gets the client address through the PROXY protocol. | HAProxy is in the path of every HTTPS request. coturn sees 127.0.0.1 for TLS clients. Caddy must come from Caddy's apt repository (2.7+).                |
| B: HAProxy terminates TURN's TLS and passes plain TURN to coturn        | coturn needs no certificate.                                                                                           | A third process holds the TURN key and sees relay traffic unwrapped. coturn still sees 127.0.0.1. The same Caddy and HAProxy work as A, plus TLS config. |
| C: nginx `stream` with `ssl_preread` instead of HAProxy                 | Same shape as A.                                                                                                       | Ubuntu's nginx pulls in the HTTP server too. Its PROXY protocol and logging need more config to turn off than HAProxy's, for the same result.            |
| D: coturn on its own box and IP, listening on 443 directly              | No proxy. coturn sees real client addresses. Relay load leaves the app box.                                            | A second box to pay for and set up. It needs the TURN secret, and Lightsail has no instance role to fetch one (0007).                                    |

## Decision

Option A. When relay use grows, we move to D (see "Moving the relay to its own box").

### Routing on 443

- HAProxy 2.8 from Ubuntu's package listens on TCP 443, IPv4 and IPv6, in TCP mode. It reads the TLS ClientHello and decrypts nothing.
- A ClientHello with SNI `turn.fidant.se` goes to coturn on 127.0.0.1:5349, unless it offers the ALPN `acme-tls/1`. Everything else goes to Caddy on 127.0.0.1:8444, with a PROXY protocol v2 header.
- The ALPN check sends Let's Encrypt's TLS-ALPN challenge for `turn.fidant.se` to Caddy, which answers it.
- Our `haproxy.cfg` replaces the packaged one and has no `log` line, so HAProxy logs nothing:

```
frontend tls
	bind :::443 v4v6
	stick-table type ipv6 size 100k expire 2m store conn_cur
	tcp-request connection track-sc0 src,ipmask(32,64)
	tcp-request connection reject if { sc0_conn_cur gt 128 }
	tcp-request inspect-delay 5s
	tcp-request content accept if { req.ssl_hello_type 1 }
	use_backend coturn if { req.ssl_sni -i turn.fidant.se } !{ req.ssl_alpn acme-tls/1 }
	default_backend caddy
backend coturn
	timeout tunnel 1h
	server coturn 127.0.0.1:5349
backend caddy
	server caddy 127.0.0.1:8444 send-proxy-v2
```

- The package's rsyslog rule for `/var/log/haproxy.log` stays, but nothing reaches it: HAProxy sends no log lines, and journald forwards nothing to rsyslog.
- A connection to coturn may sit idle for 1 hour (`timeout tunnel 1h` in its backend), so a long relayed transfer isn't cut. Every other connection gets 2 minutes (`timeout client` and `timeout server`), well above the 30-second ping the app sends on each `/signal` WebSocket. Tested on HAProxy 2.8 with the times scaled down: the tunnel timeout overrides the other two only on the coturn path.
- One source holds at most 128 connections; HAProxy closes the next one at once. A source is one IPv4 address or one IPv6 /64, as in 0006: HAProxy reports an IPv4 client on the dual-stack socket as IPv4, and `ipmask(32,64)` keeps IPv4 whole and cuts IPv6 to its /64. 128 leaves room for the app's 32 sockets per address (0006), their pages' HTTPS connections and relay connections, from people behind one NAT. Tested: the 129th connection from one IPv4 address or one /64 is closed, and another address or /64 still connects. The table holds only addresses and connection counts, in memory, and HAProxy logs nothing.

### Caddy

- Caddy comes from Caddy's own apt repository, signed with its key in `/etc/apt/keyrings/caddy-stable.asc`. That gives 2.7 or later. The test box installed 2.11.9.
- First boot stops if Caddy's repository can't be read: the key download retries 5 times, and `apt-get update` runs with `-o APT::Update::Error-Mode=any`, so any failed index fails the boot instead of installing Ubuntu's 2.6, which can't read the PROXY header. A box whose boot stopped serves nothing; `/var/log/cloud-init-output.log` shows where it stopped.
- Caddy serves HTTPS on 8444 and reads the PROXY header only from 127.0.0.1 (`listener_wrappers { proxy_protocol { allow 127.0.0.1/32 } tls }`). It speaks HTTP/1.1 and HTTP/2.
- `auto_https disable_redirects` and our own `http://` site redirect to `https://{host}{uri}`. Caddy's own redirect would name port 8444.
- A site block `turn.fidant.se { respond 404 }` makes Caddy obtain and renew that name's certificate. No HTTPS request reaches it, because HAProxy sends that name to coturn.
- Tested: the app sees the real client address in X-Forwarded-For, and a spoofed X-Forwarded-For from the client is replaced. HTTP/2 and the `/signal` WebSocket upgrade work.

### coturn

- `turnserver.conf` drops `no-tls` and adds `tls-listening-port=5349`, `cert=/etc/coturn/turn.crt` and `pkey=/etc/coturn/turn.key`. `no-dtls` stays.
- coturn 4.6.1 starts without the certificate files. UDP and TCP 3478 then work, without a TLS listener.
- A timer, `sigill-turn-cert.timer`, runs `sigill-turn-cert.service` a minute after boot and then every 5 minutes. A run that finds nothing new only compares two files. It copies Caddy's newest certificate and key for `turn.fidant.se` (the `.crt` holds the full chain) to `/etc/coturn/` when they differ. The key is 0600 turnserver:turnserver.
- The caddy user owns Caddy's certificate directory, so the script refuses a symbolic link there and reads both files as the caddy user. It writes both new files first and checks that the certificate's public key matches the key. A renewal between the two reads could otherwise pair a new certificate with the old key, and the next run would see an unchanged certificate and never repair it. A mismatched pair fails the run and is read again at the next one. Then it moves both files into place one right after the other.
- After a copy, if coturn is running, it sends coturn `SIGUSR2` if a certificate was there before, which reloads it without dropping relayed transfers. Otherwise it restarts coturn, because a coturn that started without a certificate only opens its TLS listener on restart. `SIGHUP` doesn't reload certificates. Ubuntu's `coturn.service` has no reload command, so the script uses `systemctl kill -s USR2 coturn`. A stopped coturn gets nothing and reads the files when it starts.
- The service fails, and so shows in `systemctl --failed`, while `/etc/coturn/turn.crt` expires within 14 days. It checks after any copy, so a renewal clears it at the next run. With no certificate yet, from Caddy or in `/etc/coturn/`, it succeeds. This stands in for Caddy's renewal errors, which the Caddyfile keeps out of the journal.

### URLs

- `TURN_URLS` becomes `stun:turn.fidant.se:3478`, `turn:turn.fidant.se:3478?transport=udp` and `turns:turn.fidant.se:443?transport=tcp`, plus `stun:[<IPv6>]:3478` when the box has a global IPv6 address at first boot.
- The `turns:` URL replaces the plain `turn:…?transport=tcp` URL. A network that lets TCP 3478 out lets TCP 443 out too, so the plain TCP URL adds nothing.
- The URL must use the host name. Chrome sends SNI only for a host name, never for an IP address, and offers no ALPN for TURN over TLS. HAProxy routes by SNI alone.

### What this changes in 0007

0007 stays Accepted. This record replaces two of its points:

- "No TLS or DTLS listener (`no-tls`, `no-dtls`)": coturn now has a TLS listener. Still no DTLS.
- The URL plan: "A later `turns:` URL replaces the first `stun:` URL." Under 0008, a refused send keeps only the `stun:` URLs, so the `turns:` URL replaces the plain TCP `turn:` URL instead.

### End-to-end tests

- The Docker networks suite (`pnpm e2e:networks`) has a router mode that lets only TCP 443 out. The app server listens on 443 there, and so does coturn's TLS listener. The "only TCP 443" row reaches that listener directly, with no SNI proxy. The suite's box test runs HAProxy, Caddy and coturn from the rendered `user-data.sh` and relays a transfer over TLS on 443 through HAProxy. It found two faults before deploy: the `relay-ip` one below, and Caddy 2.11 sending its upstream's address as `Host`, which made `/signal`'s origin check refuse every page. `header_up Host {host}` in the Caddyfile fixes that.
- The suite makes a self-signed certificate for `turn.sigill.test` at start. Chrome ignores `ignoreHTTPSErrors` for TURN over TLS, so the browsers start with `--ignore-certificate-errors-spki-list` and that certificate's public key hash. That trusts only that key.
- The browsers reach the relay at `turns:turn.sigill.test:443?transport=tcp`, a host name mapped through Chrome's host resolver rules, so they send SNI as in production.
- The loopback `pnpm e2e` stack keeps plain TURN over TCP and no TLS.

## Consequences

- A browser that can only reach TCP 443 can use the relay. The file stays encrypted end to end, inside TURN's TLS as well.
- coturn relays from the address a client came in on unless `relay-ip` is set, and TLS clients come in on 127.0.0.1: their relayed address would be 127.0.0.1, which no peer can reach. `user-data.sh` sets `relay-ip` to the box's private IPv4 address, next to `external-ip`, so every relay uses it and `external-ip` maps it to the public one. The box test in `pnpm e2e:networks` relays over TLS through HAProxy and caught this. It also means the relay hands out IPv4 relayed addresses only, as Chrome asks for by default. So 0007's accepted risk of reaching UDP services on the box's IPv6 address through an IPv6 relay no longer applies.
- coturn sees 127.0.0.1 as the address of every TLS client. The temporary log from 0007's runbook shows 127.0.0.1 for them, and a per-address limit in coturn couldn't tell them apart. Peer addresses, and so `denied-peer-ip`, are unaffected. 0006's caps are unaffected too: they live in the app, which still gets real addresses.
- HAProxy is in the path of every HTTPS request to the site. If it stops, the site and the TLS relay are both down. It adds one local TCP hop.
- coturn 4.6.1 serves TLS 1.2 only. Chrome and Firefox accept it.
- coturn also opens TLS on 5349 on all addresses, on 5350, and accepts TLS on TCP 3478 and 3479. Caddy listens on 8444 on all addresses. Only the Lightsail firewall keeps 8444, 5349, 5350 and 3479 closed. The firewall stays as it is: 80, 443, 22 and 3478 over TCP, 3478 and 49152–65535 over UDP.
- 0011's monthly cap closes the relay by leaving only 80, 443 and 22 open, and 443 must stay open for the site. So while the cap is active, a client still reaches coturn over TLS on 443. The relayed UDP ports stay closed to inbound traffic, but whether a peer's replies to the relay still get through depends on the Lightsail firewall tracking connections. Until that is tested or fixed (SIG-162), the cap doesn't guarantee that the relay is off.
- Caddy logs a failed TLS-ALPN challenge with the client's address under the `tls` logger. Anyone can trigger one by connecting to `turn.fidant.se` with the ALPN `acme-tls/1`. `exclude http.log.error` doesn't cover it, so the Caddyfile excludes the `tls` logger too. That also hides its children, such as `tls.obtain`, so a failed certificate renewal no longer reaches the journal. The runbook checks certificate dates instead.
- At first boot coturn starts before Caddy has the `turn.fidant.se` certificate. TLS comes up within 5 minutes of Caddy getting it, at the next timer run, through a restart. Renewals reload with `SIGUSR2` and keep relayed transfers.
- In the Chrome test, a host-name `turns:` URL made two relay allocations per peer, against one for an IP address. The cause is unknown. It costs allocations against `total-quota`, not correctness.
- Caddy now comes from a third-party apt repository. The key is pinned to a file on the box, and the box is replaced on any change to user data.
- `turn.fidant.se` now also needs a Let's Encrypt certificate, which counts toward the rate limits 0007 mentions for box replacements.

### Moving the relay to its own box

One box is right while relay traffic is small. We move coturn to its own box and IP, with coturn listening on 443 directly and no HAProxy, when any of these holds:

- Relay traffic shows up in the app box's CPU, network or Lightsail transfer allowance, or slows page loads.
- HAProxy in the path of every request becomes a problem: an outage, a fault it causes, or an HTTP/3 or other change it blocks.
- coturn seeing 127.0.0.1 gets in the way: we need per-client limits or a temporary log that tells TLS clients apart, for example to stop abuse.
- Relayed transfers grow to a share of transfers that a box replacement (5–10 minutes down) would noticeably break.

The move changes the `turn.fidant.se` A record and solves the secret hand-out that 0007 left open for a second box.

## Runbook

Additions to 0007's runbook. Use browser SSH from the Lightsail console, as root (`sudo -i`).

### Status

```sh
systemctl status haproxy caddy coturn sigill-turn-cert.timer
systemctl --failed
ss -ltnp | grep -E ':(443|8444|5349) '
journalctl -u sigill-turn-cert
ls -l /etc/coturn/
```

- HAProxy listens on 443, Caddy on 8444, coturn on 5349.
- `systemctl --failed` doesn't list `sigill-turn-cert.service`. If it does, its journal says why: a symbolic link was refused, or the certificate expires within 14 days because Caddy hasn't renewed it.
- `openssl x509 -noout -enddate -in /etc/coturn/turn.crt` shows a date well ahead. Caddy renews when a third of the certificate's lifetime is left, and the timer copies the new one within 5 minutes.
- `/etc/coturn/turn.crt` and `turn.key` exist, the key is 0600 turnserver:turnserver.
- `journalctl -u haproxy` holds no client IP addresses.

### Force a certificate reload

```sh
systemctl start sigill-turn-cert.service
```

- It copies Caddy's certificate only if it changed. To force a copy and reload anyway:

```sh
rm /etc/coturn/turn.crt
systemctl start sigill-turn-cert.service
```

- With no certificate there before, the service restarts coturn, which drops relayed transfers in progress.

# 0019: The relay only as a fallback

- Status: Accepted
- Date: 2026-11-25
- Linear: FID-191

This record amends 0007, 0009 and 0015. Read them with the replacements under Decision.

## Context

- The send page offers "Allow our relay if a direct connection isn't possible" (0008), and `docs/how-fidant-works.md` said the relay route is taken "when no direct route works".
- When the sender allows the relay and a relay is up, `joined` carries its `stun:`, `turn:` and `turns:` URLs, with TURN credentials (0006, 0008, 0015). Until FID-191 both browsers started their peer connection with all of them.
- So on every pairing that allowed the relay while a relay was up, each browser reserved a relay address, even when a direct route won (0007). The relay saw both IP addresses on every such pairing.
- ICE takes the first pair that works. In CI's networks suite, the "home routers (cone)" row ended on the relay although hole punching would have worked (runs 45648055551 and 45657096618). The TURN pair became writable before hole punching finished, Chrome selected it, and the sender's page itself reported the path `relay`. The promise of the checkbox didn't hold.
- A peer refuses a second `offer` or `answer` in an attempt (`apps/web/src/lib/peer.ts`).
- The sender ends an attempt whose data channel hasn't opened 20 s after the join (`SETUP_TIMEOUT_MS`).
- On 2026-11-25, FID-191 decided to make the relay a true fallback.

## Decision

The browsers first try the direct routes without the relay. They add the relay only when nothing has connected 3 s after the sender applies the recipient's answer. This record and `docs/how-fidant-works.md` call that step adding the relay. It works by an ICE restart.

### Direct routes first

- Both browsers start their peer connection with only the `stun:` URLs from `joined`. No browser reserves a relay address, and no traffic goes through the relay, while the direct routes are tried.
- STUN requests still go to the relay box (`stun:sto.relay.fidant.se:3478` today), so the relay box still sees each browser's IP address when that browser asks for its public address.
- `joined` doesn't change (0015, "Choosing a relay"). The browsers keep the full list, with the TURN credentials, for adding the relay.

### Adding the relay

- The relay is added only when `joined` listed `turn:` or `turns:` URLs: the sender allows the relay and a relay is up.
- When the sender has applied the recipient's answer, it waits 3 s (`RELAY_FALLBACK_MS` in `apps/web/src/lib/peer.ts`). If ICE is still not connected then and its data channel hasn't opened, it adds the full ICE server list (`setConfiguration`), restarts ICE (`restartIce()`) and sends a new offer as a sealed signal of the new kind `restart-offer`.
- ICE counts as connected when `iceConnectionState` is `connected` or `completed`; DTLS doesn't count, so a connection whose ICE is `disconnected` at 3 s also gets the relay added, unless its data channel has opened.
- The recipient adds its own full list and answers with `restart-answer`.
- ICE then tries every route again, the relay included, and can still pick a direct one.
- The recipient ignores a `restart-offer` that is in order but arrives while its ICE is connected or once its data channel is open, before it checks the offer: it leaves its connection as it is and sends no `restart-answer`. That uses up its restart: it ignores every later `restart-offer` too, even once its ICE is no longer connected.
- The sender does the same with `restart-answer`: it ignores one that is in order but arrives while its ICE is connected or once its data channel is open, before it checks the answer, and every later one too.
- So a page applies no restart SDP from the other side that arrives while its ICE is connected or once its channel is open, nor any later one, even one sealed by the holder of the signal key (our server, on an emailed link).
- These rules also catch honest signals. A `restart-offer` can cross the recipient's ICE connecting or its channel opening, and a `restart-answer` can cross the sender's. Consequences says what each crossing leaves behind.
- Each is accepted at most once per attempt: `restart-offer` only after the recipient answered the first `offer`, and `restart-answer` only after `restart-offer`. One that comes out of order, or after one that was accepted, is refused as a bad signal. A second `offer` or `answer` is still refused, so the server can't replay a first offer or answer as a restart one.
- Both must name the same two DTLS certificates as the first `offer` and `answer`, which the check number comes from (`docs/decisions/0017-check-number.md`). A page refuses the other side's restart SDP with another fingerprint as a bad signal, and closes with `setup-failed` if its own would name another. A page that ignores a restart SDP doesn't apply it either. So adding the relay can't put anyone between the browsers after the number was fixed.
- Both kinds are sealed like every other signal, with the direction and the attempt bound in. The server sees only another opaque `relay` message.
- A candidate whose `usernameFragment` is set and differs from the current remote description's is dropped silently, which drops candidates from before the ICE restart that arrive after it.
- If sending `restart-offer` or `restart-answer` fails, the peer closes with `signal-failed`. If `setLocalDescription` fails for either, it closes with `setup-failed`.
- If the sender's `setConfiguration` or `restartIce` throws, it doesn't add the relay, and the connection goes on without it. If the recipient's `setConfiguration` throws, it still answers `restart-offer`, and the connection can still go through the sender's relay address.

### What stays

- Refusing the relay (`turn: false`, 0008) is unchanged: `joined` then has only `stun:` URLs, so the relay is never added.
- The server is unchanged. The sender reads the path when its data channel opens and reports it, as before. It doesn't add the relay once its channel has opened, so no ICE restart starts after it read the path. A restart it started earlier doesn't complete on its side after that, because it ignores a `restart-answer` once its channel is open.

## Consequences

- A transfer that needs the relay starts about 3 s later, plus the time the browsers take to reserve relay addresses.
- A pairing that has connected 3 s after the sender applies the recipient's answer reserves no relay address. The relay carries less, sees fewer addresses and counts fewer allocations against `total-quota`.
- A direct route that hasn't connected 3 s after the sender applies the recipient's answer, for example on a network that loses many packets, gets the relay added and may then end up on the relay. After the ICE restart, ICE runs with the relay, so a relay pair can still win against a direct route that would also have worked.
- The relay is added at most once per attempt, and each page judges only its own connection. The sender adds it only while its ICE isn't connected and its data channel isn't open. The recipient adds its own only for a `restart-offer` that arrives while its ICE isn't connected and its channel isn't open.
- When an honest `restart-offer` crosses the recipient's ICE connecting or its channel opening, the sender has already added the relay and restarted ICE. It gets no `restart-answer`, and it doesn't take the relay back out before the attempt ends, so its browser can keep a relay allocation until then. The relay can then learn both IP addresses, although the recipient added nothing. In manual runs on 2026-11-25 with Chromium 159, the sender's browser made one allocation and asked the relay to let the recipient's address through, and the connection stayed on its first route.
- When an honest `restart-answer` crosses the sender's ICE connecting or its channel opening, the recipient has already added its relay and restarted ICE, and its browser can keep a relay allocation until the attempt ends. The sender's restart doesn't complete: it keeps its old remote description. Both browsers may then hold relay allocations. In a 60 s manual run on 2026-11-25 with Chromium 159, the connection stayed on its first route, the same host candidate pair, with messages flowing both ways. That run's TURN URL couldn't be reached, so it showed only that the route stayed among the host pairs, not what a reachable relay would do.
- Safari and Firefox weren't tested for either crossing.
- A direct route that drops after the sender skipped adding the relay isn't rescued by the relay, as it could be when the browsers gathered relay candidates from the start: neither browser has the relay, and nothing adds it later. Such a transfer fails. One that drops after a crossing may not be rescued either. Relay candidates may then exist on one side or both, but the restart completed on one side at most. That is untested. FID-91 tracks recovering through an ICE restart on a network change.
- The design relies on the browser not reporting ICE `failed` sooner than 3 s after the sender applies the recipient's answer, plus one signaling round trip. A page closes with `connection-failed` when its connection fails, so that would end the attempt before the relay could help. The end-to-end tests run only Chromium.
- The ICE server list needs a `stun:` URL for direct routes through public addresses. The server doesn't check that today: `apps/server/src/relays.ts` and `TURN_URLS` (`apps/server/src/main.ts`) accept a list without one. With such a list, every pairing that needs a public address to connect directly would get the relay added 3 s after the sender applies the recipient's answer.
- The relay box still sees each browser's IP address on every pairing that gets its `stun:` URL, from the STUN request. Once the relay is added it also sees both IP addresses from the allocations, even if a direct route then wins. When the recipient ignored `restart-offer`, it can see both from the sender's allocation alone, which names the recipient's address to let through.
- With unmodified browsers, the sender reports `relay` only after the relay was added.
- A recipient page loaded before this change treats `restart-offer` as a bad signal. It ends that attempt with a failure and closes its signaling socket, as when its connection drops.
- A sender page loaded before this change is the likelier case, because senders keep their page open. It starts with the full list and reserves relay addresses at once, but never sends `restart-offer`. A recipient page loaded after the change then starts with STUN only and never adds the relay, so it can reach only the sender's relay address. That fails for a recipient that needs its own relay, such as one on a network that blocks UDP or allows only TCP 443. A reload of the sender's page and a new link fix it: a reload drops every link the page hosts.
- A page loaded before this change still starts with the full list, so it reserves relay addresses at once and trickles relay candidates, as before. What this record says about allocations, relay candidates and the `relay` path holds for pairings where both pages were loaded after it.
- A browser whose `setConfiguration` or `restartIce` throws doesn't stop the attempt. On the sender's side the connection goes on without the relay. On the recipient's side the connection can still use the sender's relay address.
- An attempt that adds the relay sends about a dozen more `relay` messages through the server, far under its limit of 1,000 messages per socket per 30-second window (0006). Each is one more `relay` log line.
- `docs/how-fidant-works.md` and the technical web text no longer say the relay is used only when no direct route works. They say when the relay is added. The shorter user-facing texts that say the relay carries the file when the browsers can't connect directly stay as they are, because this change makes none of them untrue. It narrows when the relay can carry a file to pairings where nothing has connected 3 s after the sender applies the recipient's answer; before it, a file could already go through the relay while a direct route worked. The seven texts are the checkbox label "Allow our relay if a direct connection isn't possible" (`send.allowRelay`), the notice on a relayed transfer (`server.fileDataRelayed`), the relay route's explanation (`connection.relay.explain`), the landing page's note on the relay (`landing.relayNote`), the relay section on `/how` (`how.sections.relay`), the first section on `/security` (`security.sections`) and the privacy page's text on the relay log (`privacy.relayLog`).

# 0023: Pages on a CDN and signaling in a container, without the app box

- Status: Proposed
- Date: 2026-11-25
- Linear: SIG-259

## Context

fidant.se still runs on the app box. This record proposes moving the app off it. The work has five parts under SIG-259: SIG-260 (app code and this record), SIG-261 (signaling beside the box), SIG-262 (pages beside the box), SIG-263 (the cutover) and SIG-264 (cleanup). The status is Proposed on purpose, and `docs/decisions/README.md` lets a record merge as Proposed. This record counts as accepted only when the cutover pull request (SIG-263) sets it to Accepted. Until then it may change while SIG-261 and SIG-262 settle the open questions under Consequences, with the limit the README sets: what it says about code that is on `main` (most of it under "Changes to the app code") and the section "Amendments from this record's merge" change only in a pull request that changes that code.

In this record, "will" marks what parts 2 to 5 build. The present tense describes `main` once SIG-260 and SIG-261's first two pull requests merge: their app code, under "Changes to the app code", the signaling image, under "Signaling", the DNS records and certificate stacks, under "DNS and certificates", the registry, the release role and the release workflow, under "Deploys, and who can change what visitors run", and the app box as it runs today. None of them changes what visitors get: the box still serves fidant.se.

- One Lightsail box, the app box, does everything for the app. It serves the pages, builds the commit a maintainer promotes to the `production` branch, if it is on `main`'s first-parent history, and switches to it once the build passes (0020), holds the site's certificates in Caddy, and runs signaling. It still carries HAProxy on 443 (0010) and the fallback coturn at `turn.fidant.se` (0007), which the app uses only without a relay list (0015).
- Its first-boot script, `apps/infra/box/user-data.sh`, is about 400 lines. A change to it or to its inputs replaces the box, with 5 to 10 minutes of downtime each time (0007). In November 2026 that happened often.
- Lightsail has no instance role (0007, 0013), so the server could get AWS credentials only from a key placed by hand. A box that is replaced that often cannot keep a secret placed by hand. That is why mail is off.
- Signaling keeps its pairings in one process's memory (`apps/server/src/signaling.ts`), so it runs as one process.
- Production hosting is SIG-26, which is meant to leave AWS. Until then the app stays on AWS, so what is built here must not tie the app's code to AWS.
- SIG-259 set four aims: as little to maintain as possible; able to scale when that is needed; the strongest protection we can give ourselves and the people who use Fidant; able to leave AWS without rewriting big parts.
- The goals that follow from them:
  - A merge that changes neither server code nor the lockfile restarts nothing. A docs-only merge deploys nothing.
  - Pages load while signaling is down or being replaced.
  - The app has no machine, no operating system to patch, no Caddy, no HAProxy and no certificate to renew. The relay box is the only machine left.
  - No secret is placed by hand, and the server gets a role it can later use for mail (SIG-108).
  - One test suite runs the production shape: pages from a static host with the edge's rules, and signaling from the real image on another name.
  - The security text (`docs/how-fidant-works.md`, the site, `AGENTS.md`) changes in the same pull request as the cutover.
- Outside this work:
  - Sending mail through the role. SIG-108 does that. This work creates the role and grants it nothing.
  - A second signaling server, or links that name their server.
  - A firewall on the signaling load balancer, or signaling in more than one process (SIG-148 question 4).
  - Leaving AWS (SIG-26).
  - The cost-based relay cap (SIG-154), or any other change to the relay box.
  - A check from outside AWS that the served files match the public repository's build.
- This record answers questions 1 and 2 of SIG-148. It replaces SIG-192, which would have moved the app box to EC2 and is cancelled.

## Options considered

### The approach

| Option                                                         | For                                                                                    | Against                                                                                                                                                                                                                |
| -------------------------------------------------------------- | -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A CDN for the pages plus one container for signaling (chosen)  | The same Node process, with no machine to run, a role, and an image any provider runs. | Costs more than the box (see Consequences). AWS's load balancer decrypts signaling.                                                                                                                                    |
| A CDN plus serverless signaling: API Gateway, Lambda, DynamoDB | Nothing of ours to run or patch, and it scales by itself.                              | Locks signaling to AWS. Stores pairings, recipients' addresses and codes in a database. Throws away the audited signaling code, and local tests would run a stand-in. SIG-58 rejected it for most of the same reasons. |
| A CDN plus a small EC2 box, as SIG-192 decided                 | An instance role, with the same Ubuntu, user data and Caddy as today.                  | The machine, its user data, its replacement downtime and its patching all remain.                                                                                                                                      |

AWS App Runner was not an option either: it is closed to new customers ([App Runner availability change](https://docs.aws.amazon.com/ja_jp/apprunner/latest/dg/apprunner-availability-change.html), read in its Japanese version on 2026-11-25).

### Choices inside that approach

CloudFront's prices and plan terms below were read on 2026-11-25: [CloudFront pricing](https://aws.amazon.com/cloudfront/pricing/), [pay-as-you-go pricing](https://aws.amazon.com/cloudfront/pricing/pay-as-you-go/) and [flat-rate pricing plans](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/flat-rate-pricing-plan.html).

| Choice                       | Chosen                                                   | Turned down, and why                                                                                                                                                                                                                                                                                                    |
| ---------------------------- | -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Where TLS for signaling ends | An AWS application load balancer with an AWS certificate | Pass-through to Caddy inside the container. The load balancer is run by the same company, in the same city, as the container's host, so pass-through protects nothing more. It would add Caddy, certificate state and a volume for us to run. It may also keep AWS's firewall off the load balancer (open question 10). |
| How browsers reach signaling | Its own name, directly                                   | Through the CDN. Edges all over the world would then decrypt signaling, which carries the keys of emailed links (0012).                                                                                                                                                                                                 |
| The relay's secret fetch     | The CDN forwards `/relay-secret/*` to signaling          | Rebuilding the relay box to fetch from the signaling name. A rebuilt relay box has a new key pair, which needs a reviewed pull request, and gets no secret until it merges and a maintainer promotes it (0013, 0020).                                                                                                   |
| Paying for the CDN           | The free flat-rate plan, which has no overage charges    | Pay-as-you-go bills a flood to us: a billion requests costs about 1,200 USD. The Pro plan costs 15 USD a month and is the step up when traffic outgrows the free allowance.                                                                                                                                             |
| Where the relay master lives | AWS's secret store                                       | A new master at every start. Nothing would be stored, but pairings would get no relay for about 2.5 minutes after each start (0015).                                                                                                                                                                                    |

## Decision

The app will leave the app box. Its pages will be served from a private S3 bucket behind CloudFront, on the free flat-rate plan. Signaling will run as one Fargate container behind an AWS application load balancer in Stockholm, on its own name, `sto.signal.fidant.se`. The relay master will live in AWS's secret store. Then the app box will be deleted. The relay box stays as it is, and the app stays on AWS until production (SIG-26).

SIG-259 chose these points: signaling in one Fargate container, neither serverless (too tied to AWS) nor on an EC2 box; browsers reaching signaling on its own name, directly, not through the CDN; signaling set up like the relay, with a relay-style name and a committed list of one entry, while links stay as they are until a real second server exists; pages on S3 behind CloudFront on a flat-rate plan; TLS for signaling ending at an AWS load balancer; the CDN forwarding the relay's secret fetch; the relay box staying; the relay master in AWS's secret store; and stopping the app on the box by hand at the cutover, so old tabs fail visibly. The rest of this section is decided in this record.

### Rules

Parts 2 to 5 will keep these rules:

- `/signal` is never reachable through the CDN.
- `apps/web` holds no AWS-specific code. `apps/server` holds none outside a seam that has a neutral default. Today the only such seam is the `Mailer` type, where SIG-108 may add a sender for Amazon SES beside the SMTP one.
- No log is turned on at the CDN, its firewall or the load balancer: no access logs, no firewall logs, no sampled requests.
- Two signaling containers never run at once. Pairings live in one process's memory.
- No app code reaches visitors unless a maintainer promoted it (0020). Infra, the edge function included, goes live when its pull request merges, with the `maintainers` approval that `AGENTS.md` asks for under Merging.
- The app's release job runs no repository code while it holds AWS credentials.
- Nobody types, sees or carries the relay master.

### Pages

Part 3 (SIG-262) will build them:

- A private S3 bucket will hold the web build. Only the CDN will be able to read it, and only the release role to write it. Versioning will be on.
- One CloudFront distribution will serve `fidant.se` and `www.fidant.se`. By the plan terms, a flat-rate plan covers one apex domain and comes with AWS's firewall. So `fidant.eu` and `fidant.org`, each with `www`, will get one redirect-only distribution each. All three will be on the free plan, with its firewall. An account has exactly three free plans, a quota that can't be raised ([flat-rate pricing plans](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/flat-rate-pricing-plan.html), read on 2026-11-25), so a fourth distribution in `fidant-poc` would be pay-as-you-go. CloudFormation puts a distribution on a plan itself, and a free plan needs no approval ([AWS::PricingPlanManager::Subscription](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-pricingplanmanager-subscription.html), read on 2026-11-26). If the account cannot have the free plan, the stack's first create fails and rolls back, and a follow-up will put the three distributions on pay-as-you-go, without the plans and their web ACLs (decided on 2026-11-26).
- An edge function, `apps/infra/edge/site.js`, will take over two jobs. A distribution on a plan can share neither its function nor its web ACL with another distribution (the plan page), so each distribution has a function of its own, all three from that file, and a web ACL of its own:
  - From `serveStatic` in `apps/server/src/server.ts`: each path will get what the rule `serveStatic` applies would give it. Today that rule has five answers. Every path under `/r/` gets a receive page picked by `Accept-Language`, with `vary: accept-language` and `x-robots-tag: noindex`. A path with a file extension other than `.html` gets the file of that name. A page's path gets that page's own file. A moved path, or a page's path that ends in a slash, is redirected to the page's path. Every other path, one that ends in `.html` in any letter case included, gets the 404 page, the Swedish one under `/sv`, and status 404. Responses will carry the server's three headers: `content-security-policy`, `referrer-policy` and `x-content-type-options`, and the server's `content-type` for the file's extension, whatever type the bucket stored. Whether the free plan lets the function set the CSP is open question 2.
  - From Caddy on the box (`apps/infra/box/user-data.sh`): any host other than `fidant.se` will be redirected to `https://fidant.se` with the same path, and responses will carry HSTS, `max-age=31536000; includeSubDomains`.
- The function reads a path as `serveStatic` does: the URL parser's view first, where dot segments, percent-encoded ones too, resolve before decoding and never above the root, then the decoded path picks the answer, and the file it names is that path resolved, where climbing above the root answers 404. A path that can't be decoded answers 400. A redirect keeps the query exactly as the visitor sent it (`request.rawQueryString()`, [helper methods](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/general-helper-methods.html), read on 2026-11-26).
- The function never hands the bucket `/` or a path that ends in `/`, and the main distribution's default root object is `pages/index.html`. The CDN may list the bucket, so that a missing file answers 404 and not 403 ([GetObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html), read on 2026-11-25), and with that right a request that reached the bucket as `/` would get the list of its files.
- The function marks its choice in a request header, `x-fidant-page`, after removing any the visitor sent, and reads it back on the response, or the path when the header is not there: AWS does not say which request the response event carries ([event structure](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/functions-event-structure.html), read on 2026-11-26). If it carries the visitor's own, a visitor's header can change only the status and headers of that visitor's own response, never what the CDN caches.
- The distributions will redirect HTTP to HTTPS and compress responses, as Caddy does today. They will speak TLS 1.2 and 1.3 only (`TLSv1.2_2021`) and have no IPv6. Other methods than GET and HEAD will get CloudFront's 403, where the server answers 405.
- Each web ACL has no rules, allows every request, and has sampled requests and metrics off, as AWS's own example for the free plan has. A sample would keep each request's address and URI for three hours.
- The CSP at the edge will gain one source, `connect-src 'self' wss://sto.signal.fidant.se`, so pages can reach signaling on its own name.
- Cache rules will travel with the files, set at upload: one year and immutable under `assets/`, `no-cache` for everything else. That is what `serveStatic` sends today. The free plan allows only AWS's own cache policies, and `CachingOptimized` keeps a `no-cache` page for its minimum of 1 second at the edge ([managed cache policies](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/using-managed-cache-policies.html), read on 2026-11-25), so a release reaches every visitor within a second of its upload.
- A page's path, and every path the page rule answers with the 404 page, gets the 404 page with all the headers. A missing file, one with an extension that the bucket doesn't hold, will get the bucket's own 404 with none of them: CloudFront runs no response function on an answer of 400 or more ([restrictions](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/edge-function-restrictions-all.html), read on 2026-11-25), and headers policies of our own need a paid plan. The distributions have no custom error response, so that body is the bucket's short XML, not a page without the CSP. CloudFront keeps such a 404 for 10 seconds.
- A new page needs its path in the function's list in the same pull request, which needs a `maintainers` approval. The function goes live when that pull request merges, and the new path gets the bucket's bare 404 until a maintainer promotes the release that has the page, which the rule under Merging in `AGENTS.md` already asks for at once.
- `/relay-secret/*` will be passed on to `sto.signal.fidant.se`, uncached, GET and HEAD only (open question 6), with AWS's `CachingDisabled` and no origin request policy, so the server gets no headers about the relay box beyond CloudFront's own, and no function. The body is sealed to the relay's key (0013), so the edge cannot read it. Those answers carry the server's headers but no HSTS, and the path is passed on under every name the distribution serves, `www.fidant.se` and its CloudFront name included, because no function runs on it. The rule will go when the relay box is next replaced for another reason and its `APP_URL` can change.
- `/relay-status`, and every other path that starts with `/relay-`, will answer 404 at the edge, as the page rule answers every unknown path, so a script that still asks `fidant.se` gets no relay data and no 200. Everything that reads `/relay-status` will read it from the signaling name.
- Caddy's rules are written out in full today only in the Caddyfile in `apps/infra/box/user-data.sh`, which part 5 will delete. 0010 and `AGENTS.md` describe parts of them. This record and the edge function's own test will then be their specification.
- `FidantPages`, in `apps/infra/src/pages.ts`, builds this in `fidant-poc`, in us-east-1 with its bucket, because CloudFront takes certificates only from there and web ACLs for CloudFront exist only there. `.github/workflows/deploy-infra.yml` deploys it from `main`. It joins the CDK app only once `certificateIds.pages` in `apps/infra/src/config.ts` holds all three certificates' IDs, and it outputs the three distributions' names for the cutover. The six site names keep pointing at the box until then. AWS's pages behind each point are cited in `apps/infra/AGENTS.md`.

### Signaling

Part 2 (SIG-261) will build it:

- A network with two public subnets and no NAT gateway (SIG-58).
- An internet-facing application load balancer in eu-north-1 will listen on 443 only, with an AWS certificate for `sto.signal.fidant.se`. It will forward over HTTPS to the container's port 8443, where the server presents its own self-signed certificate, as it does behind Caddy today. Its health check will be `GET /relay-status`, which must answer 200. Its idle timeout will be 2 minutes, the same as HAProxy's now (0010); the server pings every socket each 30 seconds (open question 3), and the container's `HTTP_KEEP_ALIVE_MS` keeps the server's own idle timeout above the load balancer's (see below).
- One Fargate task, 0.25 vCPU and 0.5 GB, will have a public address for outbound traffic only: pulling the image, checking relays, and later mail. Its security group will accept 8443 from the load balancer and nothing else.
- Never two tasks: a deploy will stop the old task before it starts the new one (open question 4).
- `apps/server/Dockerfile` builds the image from the repository root. It runs `node apps/server/src/main.ts` as the user `node`, with no web build inside. The recipe has no `ENV` line, so the task will set every setting. The only directory the container writes to is `/run/sigill`, owned by `node`, mode 0700, for the self-signed certificate and the relay master file. The container will run it with `SIGNALING_ONLY=1`, on a read-only file system, with a memory-backed mount on `/run/sigill` (open question 9). On Docker 29.9.3, observed on 2026-11-26, such a mount takes the directory's mode but is owned by root, so `node` can write to it only when the mount sets the owner, as `--tmpfs /run/sigill:uid=1000,gid=1000,mode=700` does. Nobody will be able to open a shell in it.
- The container's settings will be `SIGNALING_ONLY`, `TRUSTED_PROXIES` and `PUBLIC_ORIGIN` as under "Changes to the app code", and `RELAYS_FILE=/app/apps/server/relays.json`, `RELAY_MASTER_FILE=/run/sigill/relay-master`, `CERT_DIR=/run/sigill/certs`, `STUN_URLS=stun:sto.relay.fidant.se:3478` and `HTTP_KEEP_ALIVE_MS=125000`. AWS recommends an application idle timeout larger than the load balancer's; otherwise the load balancer can send a request on a connection the application has just closed, and answer 502 ([Connection idle timeout](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/edit-load-balancer-attributes.html#connection-idle-timeout), read on 2026-11-26). Node 26.13.1 was measured closing an idle connection 1 second after its keep-alive timeout (its `keepAliveTimeoutBuffer`), so with 125000 the server closes one at about 126 seconds, above the load balancer's 2 minutes.
- The task's own role will be empty. A separate start-up role will be allowed to pull the one image, read the one secret and write logs.
- The server's log lines will go to CloudWatch Logs, kept 14 days. AWS says deletion typically follows within 72 hours after that, and can take longer in rare cases ([Working with log groups and log streams](https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/Working-with-log-groups-and-streams.html), read on 2026-11-25). So a log line will typically live 17 days at most. The site says log lines are deleted after 30 days, and 14 days keeps that true despite the lag.
- No IPv6 for the site or for signaling, as today.
- `FidantSignal`, in `apps/infra/src/signal.ts`, builds this in `fidant-poc` (AWS's pages behind each point are cited in `apps/infra/AGENTS.md`):
  - The health check speaks HTTPS, because a load balancer's speaks HTTP unless told otherwise. It runs every 10 seconds with a 5-second timeout, and 2 results in a row make a task healthy or unhealthy. The target group lets a stopped task go after 5 seconds, not the default 300, so a draining task's sockets close soon after it stops.
  - The listener names `ELBSecurityPolicy-TLS13-1-2-Res-PQ-2025-09`, TLS 1.2 and 1.3 only, which AWS recommends. Without a policy CloudFormation gives a listener one that allows TLS 1.0.
  - `routing.http.xff_header_processing.mode` is `append` and `routing.http.xff_client_port.enabled` is `false`, both written out. No access, connection or health check log is on, and nothing delivers the load balancer's logs to CloudWatch.
  - The service sets a minimum of 0 and a maximum of 100 percent of its one task, because CDK's defaults are 50 and 200. The circuit breaker rolls a failed deployment back, at its default threshold of 3 failed tasks. Availability Zone rebalancing is off: ECS turns it on for a new service, and it starts a task before it stops one. Container Insights is off. The container has no health check, and ECS Exec is off.
  - The container's one writable directory is a 1 MiB tmpfs on `/run/sigill`, mounted `noexec`, `nosuid` and `nodev`, and owned by `node` through `uid=1000`, `gid=1000` and `mode=700` (open question 9).
  - The stack joins the CDK app only once `certificateIds.signal.sto` in `apps/infra/src/config.ts` holds the signaling certificate's ID, so no listener exists without its certificate.

### The relay master

- AWS will generate the master, 64 lowercase hex characters, in its secret store when the stack is created. The task will receive it at start, in the variable `RELAY_MASTER`.
- The image's entrypoint, `apps/server/entrypoint.sh`, writes it to the file that `RELAY_MASTER_FILE` names, as 64 characters and a newline like the file the server makes itself, mode 0600, and removes it from the environment before Node starts. It writes the value with a shell builtin, so the value is in no program's arguments, and prints nothing that holds it. So the server still reads a file, its code does not change (0015), and no child process inherits the value.
- A container health check, or any command run in the container from outside, would start from the task's environment and get `RELAY_MASTER` in its own. So the task will have neither: the load balancer's health check is the only one.
- AWS will make a new master too: raising a generation number in `apps/infra/src/config.ts` will make the stack generate a fresh secret and restart the task. Nobody types or sees the value.
- Production will stop relying on 0015's `/var/lib/sigill` rule: the container's settings will say which relay list and which master file the server reads.
- The generation number, `relayMasterGeneration`, is part of the secret's logical ID in `FidantSignal`. A change to how AWS generates the secret would only make a new version under the same ARN ([AWS::SecretsManager::Secret](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-secretsmanager-secret.html), read on 2026-11-26), which no task definition notices, and a running task keeps the value it started with ([Pass Secrets Manager secrets](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/secrets-envvar-secrets-manager.html), read on 2026-11-26). A new logical ID makes a new secret with a new ARN, so the task definition gets a new revision and the service a new deployment.

### 0015's runbooks without a shell

0015 has three runbooks that run as root on the app box. Once this record is Accepted they will work as below. Until then 0015's runbooks, as later records amend them, are the ones in force. This record gives no commands: they are written, following `docs/decisions/README.md`, when the resources they name exist.

- **Turn the relay list off at once.** A maintainer will deploy `FidantApp` by hand from a branch that turns the list off in the container's settings, then open the pull request for that branch. It will take about five minutes instead of seconds, and CDK stays the only source of the container's settings. 0015's version can fall back to `turn.fidant.se`. This one cannot: the container will read one secret, the relay master, and the box's TURN secret stays on the box (0007). The server takes `TURN_URLS` only together with `TURN_SECRET_FILE`, so with the list off it will hand out only the `stun:` URL in `STUN_URLS`: browsers will still learn their public address from the relay box, but get no relay. To cut the relay box off completely, the same hand deploy also clears `STUN_URLS`. Pairings then get no ICE server at all, and only pairs that connect over local addresses still work.
- **New secrets for every relay.** Raise the generation number and deploy the same way. Then 0013's "A leaked secret" runs on the relay box as before, comparing `current`'s time with when the new task started.
- **A leaked relay key.** As in 0015, the new secrets must come only after the running release holds the new key. Without a shell, the running release will be read from the task: its image carries the commit it was built from, in the label `org.opencontainers.image.revision`, which `apps/server/Dockerfile` sets from the build argument `REVISION` and the release workflow sets to the promoted commit. A release whose image inputs did not change keeps the image it has, so the label can name an earlier commit than the one promoted. `apps/server/relays.json` is one of those inputs, so it is the same at both.
- Their status check will read `https://sto.signal.fidant.se/relay-status`.

### DNS and certificates

- `FidantDns` will point the six site names at the distributions and `sto.signal.fidant.se` at the load balancer. The site names' records have a 60-second lifetime from SIG-261's second pull request, well before the cutover. `turn.fidant.se` and `sto.relay.fidant.se` keep 30 minutes.
- Each apex's CAA record names Let's Encrypt, Sectigo and `amazon.com`, and allows no wildcard. AWS issues only where CAA names `amazon.com`, `amazontrust.com`, `awstrust.com` or `amazonaws.com`. It checks CAA after it validates a name, and a certificate it refuses for CAA needs a new request ([CAA records](https://docs.aws.amazon.com/acm/latest/userguide/setup-caa.html), [CAA troubleshooting](https://docs.aws.amazon.com/acm/latest/userguide/troubleshooting-caa.html)). That answers open question 8.
- Certificates come from AWS, validated through DNS, in two stacks in `fidant-poc`. `FidantPagesCerts`, in us-east-1 because CloudFront requires it, holds three, one per distribution, each for an apex and its `www`. One certificate per distribution keeps each flat-rate plan to one apex beyond doubt, at no extra cost: the validation records are per name either way. `FidantSignalCerts`, in eu-north-1, holds one for `sto.signal.fidant.se`, for the load balancer. `fidant-poc` is bootstrapped in us-east-1, as `AGENTS.md` requires for a stack in a new region.
- A certificate whose zone is in another account keeps its stack waiting until its validation record resolves (open question 5), and the deploy workflow runs one deploy at a time. So the certificates live in stacks of their own, one per region, that CI never deploys, as with `FidantCi`. No stack imports from them: `cdk deploy` deploys a stack's dependencies with it, so CI would deploy them, and an export would pin a certificate against replacement. A maintainer deploys them once by hand. While they wait, a pull request will add the validation records to `apps/infra/src/config.ts`, `FidantDns` will publish them, and the hand deploys will complete. The records are read from `aws acm describe-certificate`. ACM gives each name one record per account, the same in every region, and stops trying 72 hours after it makes the record; the certificate then needs a new request ([DNS validation](https://docs.aws.amazon.com/acm/latest/userguide/dns-validation.html)). So the records' pull request must merge within 72 hours of the hand deploy.
- The certificates' IDs will be copied by hand into `config.ts`, and the stacks that use them will build their ARNs from the account and region. The distributions' and the load balancer's names will be copied by hand into `config.ts` too, the way `boxAddress` is today.

### Changes to the app code

These are on `main`: the first four from SIG-260, `STUN_URLS` and `HTTP_KEEP_ALIVE_MS` from SIG-261's first pull request. Each is off unless set, so none of them changes how a local run, `pnpm e2e` or the app box behaves.

| Setting              | Read by       | What it does                                                                                                                                                                                                                                                                                                                                                                               |
| -------------------- | ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `SIGNALING_ONLY`     | The server    | `1`: the server serves no pages. It answers `/signal`, `/relay-status` and `/relay-secret/<id>`, and 404 for every other path. Unset or empty: pages as before. Any other value stops the server.                                                                                                                                                                                          |
| `PUBLIC_ORIGIN`      | The server    | Already the origin of emailed links (0012). Now also the one origin, besides the page's own, that the WebSocket accepts, and valid without the mail settings. Anything but an `https://` origin with no path stops the server.                                                                                                                                                             |
| `TRUSTED_PROXIES`    | The server    | Comma-separated address ranges, such as `10.0.1.0/24`. A peer in one of them is trusted to write `X-Forwarded-For`, as a loopback peer is (0006). A value that doesn't parse, or a range that doesn't start at its first address, stops the server.                                                                                                                                        |
| `SIGNALS_FILE`       | The web build | The path of a JSON list of signaling servers. The build takes the page's signaling address from the first entry. Unset: the page opens its WebSocket to the host it was loaded from, as before.                                                                                                                                                                                            |
| `STUN_URLS`          | The server    | 1 to 4 `stun:` URLs, separated by commas, such as `stun:sto.relay.fidant.se:3478`. With no relay list and no `TURN_URLS`, `joined` carries them with no credentials, whatever the sender's relay choice. A relay list or `TURN_URLS` takes their place. Anything but 1 to 4 `stun:host[:port]` URLs with a port from 1 to 65535 stops the server, even where the setting would be ignored. |
| `HTTP_KEEP_ALIVE_MS` | The server    | Whole milliseconds from 1000 to 299000. The server closes an HTTP connection idle for 1 second longer than this, and gives a request 1 second longer than this to send its headers. Unset: Node's defaults, 6 seconds idle and 60 seconds for the headers, as before. Any other value stops the server.                                                                                    |

- `siteSettings` in `apps/server/src/settings.ts` reads the five server settings. Its error messages quote nothing from the configuration.
- The origin check (`sameOrigin` in `apps/server/src/signaling.ts`) accepts an upgrade with no `Origin` header or one whose host matches the `Host` header, as before, and now also one exactly equal to `PUBLIC_ORIGIN`.
- The address rule (`clientAddress` in the same file) takes the rightmost `X-Forwarded-For` entry from a loopback peer, as before, and now also from a peer in `TRUSTED_PROXIES`. The address is still only a key in an in-memory count, never logged (0006).
- `apps/web/signals.json` holds one entry, `sto`, with `wss://sto.signal.fidant.se/signal`. `signalingUrlFrom` in `apps/web/src/lib/signaling-list.ts` stops the build unless the list is a non-empty array whose entries have exactly an `id`, unique and shaped like a relay's (`^[a-z][a-z0-9]{1,15}$`), and a `url` of the form `wss://<host>/signal`. Links don't change: they still name no server.
- fidant.se sets no `TRUSTED_PROXIES`, `STUN_URLS` or `HTTP_KEEP_ALIVE_MS`, and the box builds the web client without `SIGNALS_FILE`. The box sets `PUBLIC_ORIGIN` only while mail is on, and then to `https://fidant.se`, the origin its pages already have, so the origin check accepts nothing new there.

What the later parts will add:

- From its first start in part 2 (SIG-261), the container will set all five server settings: `STUN_URLS` and `HTTP_KEEP_ALIVE_MS` as under "Signaling", and these three:
  - `SIGNALING_ONLY=1`. No web build will be inside the image, and without the setting the server stops when it finds none.
  - `TRUSTED_PROXIES`, set to the load balancer's subnets. Every connection will reach the container from the load balancer, so without it the per-address limits would count every socket against the load balancer's own addresses. An application load balancer appends the client's address as the last `X-Forwarded-For` entry only under two of its settings ([X-Forwarded headers](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/x-forwarded-headers.html), read on 2026-11-25). `routing.http.xff_header_processing.mode` must be `append`, its default. With `preserve` the header reaches the container unmodified, so a client would write the rightmost entry itself and could choose the address its sockets count against, which gets it past the per-address limits. With `remove` no header reaches the container. `routing.http.xff_client_port.enabled` must be off: with it on, the entry is `address:port`, which is not a plain address and is ignored, and the page does not state its default. With `remove` or a port in the entry, every client counts against the load balancer's own addresses and shares their limit. Part 2's stack will set both attributes explicitly.
  - `PUBLIC_ORIGIN=https://fidant.se`. Pages loaded from `https://fidant.se` through the CDN, first in part 3's trial, will open `wss://sto.signal.fidant.se/signal`, and the origin check refuses them without it. Set from the start, it will need no later change to the container.

### Deploys, and who can change what visitors run

- Infrastructure deploys as today: `.github/workflows/deploy-infra.yml` from `main`, with its paths protected and a `maintainers` approval.
- The app deploys from the `production` branch, which only maintainers can move (0020). The release workflow follows that branch too, so 0020's rule holds for it: no app code reaches visitors unless a maintainer promoted it. In this record a release is what a promotion starts: a run of the workflow below.
- `.github/workflows/release.yml` runs on a push to the `production` branch, one run at a time, in two jobs:
  - **Build job, with no AWS credentials and no secrets.** It checks that the commit is on `main`'s first-parent history with the box's test (0020): it fails with `refused <sha>: not on main` when `git rev-list --first-parent refs/remotes/origin/main` doesn't list the commit, and with `could not check <sha> against main` when git lists nothing. Then it computes the image's key, builds the server image and hands it on as an artifact. It builds the image on every run, because it cannot see the registry, and builds it on x86 (`ubuntu-latest`), the architecture the task will run. From part 3 it will also build the web client.
  - **Release job, with credentials, running no repository code.** It checks out nothing and runs only pinned actions, git (`ls-remote`, before it signs in), the aws CLI, docker and jq. It releases the image first, as below. From part 3 it will then upload the files, assets first and then pages, and keep old assets, so open pages keep working. It will upload them only once the image step has succeeded, so no page goes live against a server that failed. The step also succeeds when it skips an image that failed before (see "Rollback"), and the pages then go live against the image `live` names, which can lack server changes they rely on.
- The build job's check has a gap that the box's check lacks. GitHub runs the workflow file of the pushed commit, so a commit pushed to `production` that is not on `main` runs its own version of the workflow, which need not check anything, and that version's release job gets the role's credentials. The box runs its own check, written at first boot, so it still refuses such a commit. Only maintainers can move `production`, so the gap needs a maintainer's push or a maintainer's account. Until it closes, the rule that the release job runs no repository code while it holds credentials holds only for a commit on `main`. SIG-285 closes it before the cutover (SIG-263). Tags that a release pushes while the gap is open stay, because they are immutable and the release role cannot delete them, so closing the gap must also retire them, for example by changing the `inputs-`, `failed-` and commit tag prefixes in the same change.
- The service's definition will belong to the infra deploy and name the tag `live`, so a release needs no right to change the definition.
- The registry `fidant-signal`, in `FidantApp`, keeps every tag immutable except `live`. An image pushed by a release has its commit as a tag and `inputs-<key>` as another, and an image whose release rolled back also gets `failed-<key>` (see "Rollback"). None of these tags ever moves. The registry's one lifecycle rule expires only untagged images, 7 days after their push, so moving `live` leaves the old image its other tags and nothing a task may still pull expires. Deleting a `failed-<key>` tag removes only that tag, because the image keeps its other two.
- A release pushes a new image and restarts signaling only when the image's key changes. The key is a hash of the git objects, at the promoted commit, of `apps/server`, `packages/protocol` and the root `package.json`, `pnpm-lock.yaml` and `pnpm-workspace.yaml`, which the workflow lists once, in `IMAGE_INPUTS`. They hold everything the image is built from except the build step's own command (its flags, its build argument and the runner's platform), so a change there takes effect with the next change to an image input. The inputs hold the rest: the recipe, `apps/server/Dockerfile` and `apps/server/Dockerfile.dockerignore`, with the Node image the recipe pins by digest, and the files the second lets in. Those are the three root files, `apps/server/package.json`, `apps/server/relays.json`, `apps/server/entrypoint.sh`, `packages/protocol/package.json`, and `apps/server/src` and `packages/protocol/src` without their tests. `apps/e2e/src/release.test.ts` checks that every file the allowlist lets in lies under one of them. So a change anywhere under `apps/server` or `packages/protocol`, tests included, restarts signaling. So does any change to the one lockfile, which holds every package's dependencies, even one that changes only a dependency of the web client. A release that changes only web code restarts nothing, unless it is the first release after a maintainer deleted a `failed-<key>` tag, which tries that image again (see "Rollback").
- The image's release, step by step:
  - Before the job signs in, a step reads `production`'s tip with `git ls-remote` and refuses unless the run's commit is that tip, so a run for an older commit never gets credentials and never moves `live` back to an older image. A re-run keeps the commit of the run it re-runs (https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs), so re-running an older run refuses. Re-run the newest run, the one for `production`'s tip, or promote a later commit.
  - If no image has the key's tag, the job pushes the one it built under its commit, unless an image already has that tag, and gives that image the key's tag. A release whose key already has an image pushes nothing.
  - If `live` already names that image, the job ends there. If that image has the tag `failed-<key>`, the job ends there too, with a warning, before `live` moves (see "Rollback"). Otherwise it reads the service. With no cluster yet, or a cluster without the service, it moves `live` and deploys nothing, so the first image gets `live` before the service exists. With any other answer than an active service, it fails before `live` moves.
  - At its top the step traps SIGINT (exit 130) and SIGTERM (exit 143), so a cancel ends it as soon as the running command returns, and at once while it sleeps. So after `live` moves, the call in flight and the exit trap's own two calls must fit in the 10 seconds the runner gives a cancelled step. With an active service, the step then waits at most 20 minutes until the service has one deployment and that deployment is COMPLETED, so no deployment starts while the service rolls back. Then it installs an exit trap, moves `live`, asks the service for a new deployment and follows that deployment's `rolloutState` for at most 30 minutes. COMPLETED, with no other deployment left, is success. The exit trap moves `live` back to the image it named before and says so only after the move succeeded, unless the run ended in success or after it moved `live` back itself. So every other end puts `live` back: a failed call (a describe error, a refused update, an unexpected answer), a wait that runs out, a deployment that leaves the list, and a cancel. If that move fails, the log says `live` still names the new image, and a release with these inputs ends without deploying ("live already names") until `live` moves. Both waits sleep with `sleep 15 & wait $!`, because a trapped signal does not interrupt a foreground `sleep`. Observed in local runs of the step: the trap ran on `exit 1`, on a `set -e` failure, on SIGINT (exit 130) and on SIGTERM (exit 143), each sent to the shell alone during a wait, on bash 3.2.57 (macOS) and bash 5.2.15 (Debian bookworm). Without the INT trap, a SIGINT to the shell alone was dropped while a foreground `sleep` ran. GitHub documents the cancel sequence (https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-cancellation): the runner sends SIGINT to the step's entry process, SIGTERM after 7500 ms if it has not exited, and kills the process tree 2500 ms after that. A kill after that grace period, or SIGKILL, which no trap catches, can still leave `live` on an image no one has confirmed. The waits are bounded by the wall clock, not by a count of polls, and the role's session lasts 2 hours (`MaxSessionDuration`, and the workflow asks for it), above the job's 100 minutes, so the calls after the waits still have credentials.
- **Rollback.** A new task that fails its health check makes the service go back to the previous image by itself (open question 4): the job's deployment turns FAILED. The job then waits at most 30 minutes for the service to settle, moves `live` back to the image it named before the move, tags the new image `failed-<key>`, and fails. A deployment that leaves the list is not that proof: another deployment, such as a CloudFormation update, can replace it, so the job fails, moves `live` back and tags nothing, and the next release with these inputs tries the image again. A deployment that cannot start moves `live` back and fails without that tag, since the image never ran, so the next release with the same key tries it again. A wait that runs out fails the job and moves `live` back without that tag. After the update call succeeded, any such early end moves `live` back while the deployment may still complete and run the new image. The service then runs the new image while `live` names the previous one until the next release, and an infra deploy in between would roll the service back to the previous image. A later release whose key has an image tagged `failed-<key>`, one that changes only web code included, moves nothing and starts no deployment: it warns that the server image for these inputs failed before and is not deployed, names the hand step, and succeeds, so from part 3 it will still upload its pages. The hand step is a maintainer deleting the tag with their own sign-in (`AGENTS.md`, Releasing), since the release role cannot delete a tag; the next release, or a re-run of the newest release run, then tries the image again. A re-run of an older run refuses (see "The image's release"). So `live` names the running image after every release that succeeds, rolls back, cannot start its deployment or skips a failed image, and a later infra deploy cannot roll a bad image out again. Any other bad release is undone by reverting on `main` and releasing again; the bucket's versions are the fallback.
- The release job signs in as the role `fidant-release`, which trusts only tokens of the GitHub environment `app`, whose only deployment branch is the `production` branch. `FidantCi` in `fidant-poc` holds it, deployed by hand as today, and `apps/infra/src/stacks.test.ts` pins its rights to exactly these:
  - `ecr:GetAuthorizationToken` on `*`, because it has no resource type.
  - `ecr:BatchCheckLayerAvailability`, `ecr:InitiateLayerUpload`, `ecr:UploadLayerPart`, `ecr:CompleteLayerUpload`, `ecr:PutImage` and `ecr:BatchGetImage` on the repository `fidant-signal`.
  - `ecs:DescribeServices` and `ecs:UpdateService` on the service `fidant-signal` in the cluster `fidant`. A Deny refuses `ecs:UpdateService` on every service when the request turns on commands run in the task (`ecs:enable-execute-command` is `true`).
  - `s3:PutObject` on the objects in the bucket `fidant-pages-<account>`, only when that bucket is in the role's own account (`s3:ResourceAccount`).
  - The cluster, the service and the bucket don't exist yet. The grants name them by the fixed names in `apps/infra/src/config.ts`. AWS's pages: [pushing an image](https://docs.aws.amazon.com/AmazonECR/latest/userguide/image-push-iam.html), [ECS actions and condition keys](https://docs.aws.amazon.com/service-authorization/latest/reference/list_amazonelasticcontainerservice.html) and [S3 condition keys](https://docs.aws.amazon.com/AmazonS3/latest/userguide/amazon-s3-policy-keys.html).
- The order is fixed, for the reason `AGENTS.md` gives for the `production` environment: first the environment `app`, with its branch policy and the account ID as its secret, then `FidantCi` with the role, then the workflow. A workflow run creates a missing environment with no branch policy, and any branch could then get a token the role trusts. A maintainer creates the environment, because agents never change repository settings, and deploys `FidantCi` by hand, because CI never deploys it.
- The app has its own workflow, role and environment, and does not ride along with the CDK deploy. That keeps infrastructure on `main` and the app on the `production` branch.

## Consequences

### Cost

SIG-259's estimates of 2026-11-25, per month: the container about 10 USD, three public IPv4 addresses about 11 USD, the CDN nothing on the free plan, the secret 0.40 USD, and cents for logs, the registry and the bucket. That is about 22 USD plus the load balancer. In eu-north-1 the load balancer costs 0.02394 USD an hour, 17.48 USD a month, and 0.0076 USD for each capacity unit-hour it uses ([AWS's price list for Elastic Load Balancing in eu-north-1](https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/AWSELB/current/eu-north-1/index.json), published 2026-11-25). The relay box's 7 USD stays, so the total is about 47 USD a month plus capacity units. Today the app box and the relay box cost about 14 USD together.

### What gets better

- A release that changes nothing under `apps/server` or `packages/protocol` and not the lockfile will restart nothing, and pages will load while signaling is down or being replaced.
- No machine will run the app: no box replacement, no operating system to patch, no Caddy, HAProxy or certificate to renew.
- The server will get a role, so mail can later work without a secret placed by hand (SIG-108).
- The server's log lines will live 14 days, typically 17 at most, where the box's journal keeps them 29.

### What gets worse

- A server release will mean about a minute without signaling, against a few seconds today, because a new task starts only after the old one stops. It happens only when the image's key changes: anything under `apps/server` or `packages/protocol`, tests included, or the lockfile, which a dependency bump for the web client alone changes too. Sender pages reconnect by themselves.
- IAM cannot hold the release role to one task. `ecs:UpdateService` has no condition key for the desired count, so the role could raise it. "Never two" rests on the reviewed workflow, which never sets the count, not on IAM.
- Turning the relay list off at once will be a hand deploy of about five minutes, and will leave pairings with only the STUN server that `STUN_URLS` names, or with none when the same deploy clears it too (see "0015's runbooks without a shell").
- AWS's load balancer will decrypt signaling, including an emailed link's key on its way to the server (0012). Today signaling is decrypted only on our box, by Caddy and the server.
- A CDN location near each visitor will see the visitor's address and the paths they load, including the link ID on `/r/<id>`. Today our box is the only part of our infrastructure that sees both a visitor's address and the paths they load.

### Open questions

Apart from 7 and 8, no AWS doc or observed run settles any of these yet. Where a plan page is quoted, it was read on 2026-11-25, but it does not settle the question. Each gets a doc citation or an observed run in the pull request that relies on it.

1. **The free flat-rate plan.** Whether the account qualifies (the plan page excludes accounts "using AWS Free Tier"), whether the plan compresses, and what its dashboards keep about visitors. AWS's pages answer the rest: a zone in another account only keeps its own costs off the plan, three free plans are an account's whole quota, and CloudFormation puts a distribution on a plan (see "Pages"). If the account can't have the free plan, the distributions go on pay-as-you-go (decided on 2026-11-26). If the plan fails otherwise, the choice between Pro and pay-as-you-go is made again in this record. Not verified.
2. **The edge function may set the CSP on the free plan.** The plan page puts custom header policies on the 200 USD plan and includes functions on all plans, and in a viewer response only `Warning` and `Via` are read-only ([restrictions](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/edge-function-restrictions-all.html)). Not verified: the trial reads the headers.
3. **The load balancer.** That WebSocket pings keep its idle timer from firing, and that it forwards to a target with a self-signed certificate. AWS says any data sent or received resets the timer, and names no frame type ([connection idle timeout](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/edit-load-balancer-attributes.html#connection-idle-timeout)), and that the load balancer doesn't validate a target's certificate ([target groups](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/load-balancer-target-groups.html#target-group-routing-configuration)), both read on 2026-11-26. The observed run is pending.
4. **The service.** That a failed deployment goes back to the previous image even though `live` has moved, that the secret reaches the entrypoint, that a single task is replaced with no overlap, and that a task with no NAT gateway pulls its image over its public address. Read on 2026-11-26: a rollback reuses the last successful service revision ([service revisions](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/service-revision.html)), which records the image digest ([service revision properties](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/service-revision-property.html)); a secret reaches the container when it starts ([Pass Secrets Manager secrets](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/secrets-envvar-secrets-manager.html)); a maximum of 100 counts only RUNNING and PENDING tasks, and no page says whether a draining task holds the slot ([DeploymentConfiguration](https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_DeploymentConfiguration.html)); a task pulls through its own public address ([Fargate task networking](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/fargate-task-networking.html)). The observed run is pending.
5. **A certificate stack waits** for a validation record in another account, and completes once it resolves. Not verified.
6. **Forwarding `/relay-secret/*`** uncached to another origin under the free plan, which allows 5 cache rules. Not verified.
7. **A missing file in a private bucket** answers 404, not 403. Answered by S3's [GetObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html) page: S3 answers 404 to a caller that may list the bucket, and the bucket policy lets the main distribution list it (see "Pages").
8. **AWS issues no certificate** while the CAA records name only other issuers, and `amazon.com` is the value that allows it. Answered by AWS's [CAA records](https://docs.aws.amazon.com/acm/latest/userguide/setup-caa.html) page, and the records now name `amazon.com` (see "DNS and certificates").
9. **Memory-backed mounts on Fargate.** AWS announced them in January 2026 ([tmpfs on Fargate](https://aws.amazon.com/about-aws/whats-new/2026/01/amazon-ecs-tmpfs-mounts-aws-fargate-managed-instances/)), and the task definition reference for Fargate lists `tmpfs` ([task definition parameters](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task_definition_parameters.html)), both read on 2026-11-26. Whether the mount can be owned by `node` (uid 1000) is not settled: on Docker a mount is owned by root unless it sets the owner, and the mount options list names `uid`, `gid` and `mode` but shows no way to give them a value ([Tmpfs](https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_Tmpfs.html)). `FidantSignal` writes `uid=1000`, `gid=1000` and `mode=700`, as Docker takes them. The first task settles it: ECS refuses the task definition, the task stops when the entrypoint can't write the master, or it runs. If it fails, the fallback is an empty bind mount on the task's encrypted disk, which is owned by root with mode 0755 unless the image has a `VOLUME` line for `/run/sigill` ([bind mounts](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/bind-mounts.html)). That fallback needs the line in `apps/server/Dockerfile`, and this record then stops calling the directory memory-backed. The observed run is pending.
10. **AWS's firewall cannot attach to a pass-through load balancer.** This only supports a choice already made. Not verified.

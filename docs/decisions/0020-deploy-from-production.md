# 0020: Deploying the app from a production branch

- Status: Accepted
- Date: 2026-11-25
- Linear: FID-169

This record amends 0013 and 0015. Read them with the replacements under Decision.

## Context

- Until FID-169, `fidant-deploy` on the app box read `main` from GitHub every minute and built each new commit. The box picked up a merge to `main` within about two minutes and served it once the build passed. No maintainer step came between the merge and the site.
- The `sensitive-paths` ruleset asks for a `maintainers` approval on the paths that AGENTS.md lists under Merging, among them `apps/infra/**` and `apps/server/relays.json`. It doesn't cover `apps/web`, `packages/protocol` or the rest of `apps/server`, the code that decides whether keys and file content stay in the browser. Those merge with green CI and the Claude reviewer's approval, and agents may merge them (AGENTS.md, Merging).
- So one compromised GitHub account, or one pull request that misleads the reviewer, could serve every visitor code that sends keys out, within minutes. The repository is public, so anyone can read that path.
- `.github/workflows/deploy-infra.yml` deploys the CDK stacks on a push to `main` that touches the files it checks out. All of them need a `maintainers` approval (repository admins can bypass that rule).

## Options considered

### How app code reaches fidant.se

| Option                                                                   | For                                                                                    | Against                                                               |
| ------------------------------------------------------------------------ | -------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| `apps/web/**`, `apps/server/**` and `packages/**` in `sensitive-paths`   | One ruleset change.                                                                    | Nearly every pull request waits for the other developer.              |
| The box serves a `production` branch that only maintainers move (chosen) | `main` keeps merging as it does. A maintainer decides when app code reaches fidant.se. | App code waits for a promotion, and infra doesn't (see Consequences). |

### How a maintainer promotes

| Option                                       | For                                                       | Against                                                      |
| -------------------------------------------- | --------------------------------------------------------- | ------------------------------------------------------------ |
| A fast-forward push to `production` (chosen) | No workflow, and no token in CI that may move the branch. | Each promotion is a command a maintainer runs.               |
| A workflow behind an environment approval    | One click in GitHub.                                      | The workflow's token must be allowed to update `production`. |

### What the box accepts

| Option                                             | For                                                                                                                                                                                                | Against                                                                                                                                                                                                |
| -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Whatever `production` points at                    | Nothing to check on the box.                                                                                                                                                                       | The rulesets limit who moves the branch, not to which commit. A maintainer's mistake, or an agent with a maintainer's credentials, ships that commit.                                                  |
| A commit reachable from `main`                     | Only commits that reached `main` through a pull request ship.                                                                                                                                      | It also accepts the intermediate commits of a merged pull request's branch. A branch can add code and remove it again, so review sees only the result, and those commits never passed CI on their own. |
| A commit on `main`'s first-parent history (chosen) | Only the commits `main` itself went through ship. After the first commit, each is a merged pull request's result with green CI, unless the pull request was merged by rebasing (see Consequences). | A fix can't ship alone from `production`. It ships with everything merged to `main` before it.                                                                                                         |

### Where infra deploys from

| Option                     | For                                                                                            | Against                                                                         |
| -------------------------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| `main`, as before (chosen) | `sensitive-paths` already asks a maintainer to approve every file the infra deploy checks out. | Infra goes live at the merge and the app at the promotion (see Consequences).   |
| The `production` branch    | Infra and app go live together.                                                                | A second maintainer step for changes that already need a maintainer's approval. |

## Decision

The app box serves the `production` branch. Only the `maintainers` team moves it, only forward, and the box builds only a commit on `main`'s first-parent history: `main`'s tip, its first parent, that commit's first parent, and so on. How to promote and roll back is in `AGENTS.md`, under Releasing.

- `fidant-deploy` (`apps/infra/box/user-data.sh`) reads `refs/heads/production` every minute. While the branch is missing, it logs `no production branch` and builds nothing.
- Two rulesets, set by hand in GitHub and not in this repository, protect the branch. `production` refuses deleting it and moving it other than forward, with no bypass. `production-maintainers` refuses updates from anyone but the `maintainers` team. Repository admins can still change the rulesets.
- Right after cloning, before checkout and `pnpm install`, the box lists that history with `git rev-list --first-parent refs/remotes/origin/main`, as `fidant`. The full ref keeps a tag named `origin/main` from shadowing the branch.
  - The sha is in the history: it builds the commit.
  - Git printed the history and the sha isn't in it: it logs `refused <sha>: not on main` and writes `/opt/fidant/failed-<sha>`, so it doesn't try that commit again until the file is deleted.
  - The check itself fails, because git or `runuser` fails or git prints no history, for example after a missing object, a corrupt clone or a full disk: it logs `could not check <sha> against main`, writes no marker, and the next run tries again.
- AGENTS.md says that agents merge pull requests only into `main`, and never push to `production` or promote a release. A Claude Code hook, `.claude/scripts/production-guard.sh`, blocks the common commands that would. It is a guardrail, because agents push with a maintainer's credentials and the rulesets let those pushes through. It covers only agents' Bash calls in Claude Code. It removes quotes, joins continued lines and splits the command on `;`, `&`, `|`, `(`, `)`, `<`, `>` and backticks, then blocks:
  - a `git push` that names `production` as a refspec destination or a bare ref, `--delete … production` included. It also blocks when any other git command in the same Bash call names `production` that way, before or after the push. Global options before `push` don't hide it when the hook knows them and their values hold no spaces and none of the characters it splits on: `-C`, `-c`, `--git-dir`, `--work-tree`, `--namespace`, `--config-env`, `--attr-source` and `--shallow-file` with a separate value, and any `--opt=value` or bare flag;
  - a `git push --mirror`;
  - any `git push` whose repository has a local `refs/heads/production` branch. The repository comes from the tool's working directory, a literal `cd <path>` earlier in the same Bash call, and the global options before `push`. A `production` tag alone doesn't count;
  - a `gh api` write that names the branch as `refs/heads/production` or `branches/production/`, in a path or a field value, or as a field value `…=production`. A write is `-f`, `-F`, `-X`, `--method`, `--field`, `--raw-field` or `--input`, a short flag also inside a group such as `-iX`. A command counts as a read only when `-X GET` or `--method GET` comes right after `gh api` and no other method appears. `environments/production` in a path stays allowed;
  - `gh pr create` and `gh pr edit` with `--base production`, `-B production` or their `=` forms, `-B` also inside a short-flag group such as `-fB production`.
- The hook misses other ways to move the branch, among them:
  - refspecs or branch names built at run time;
  - a quoted global option value that contains a space or a character the hook splits on, which hides the whole `git push` from the hook;
  - backslash and ANSI-C quoting, such as `\git`, `pro\duction` or `$'production'`;
  - for the local `production` branch check, a repository reached through `~` or `$VAR` in `cd`, `-C` or `--git-dir`, through a `GIT_DIR=` prefix, or through `pushd`;
  - for the same check, a `cd` that doesn't start its part, as in `if cd …; then` or `{ cd …; }`;
  - a push destination from config: one that an earlier Bash call set, such as a `remote.origin.push` refspec, or an upstream on `production` with `push.default=upstream`, which a bare `git push` then follows, and one read from a file or a pipe, such as `-c include.path=/dev/stdin`;
  - other environment variables before git, such as `GIT_WORK_TREE` or `GIT_CONFIG_*`, and `--config-env` reading an exported variable, which make the hook's own check fail open. So does a global option before `push` that makes the hook's own git fail or hang, such as a `-c include.path` that names a fifo;
  - git aliases, calling `git-push` directly, and plumbing such as `send-pack`;
  - gh aliases, `gh api graphql`, and `gh api` bodies read from a file (`--input`, `-F key=@file`);
  - a `gh api` write with the text `gh api -X GET` inside a later argument, such as a header value, which makes the write look like a read;
  - `gh pr merge` of a pull request that already targets `production`, which AGENTS.md's rule to merge only into `main` covers, and `gh pr -R <owner>/<repo> create …`.
- It also blocks some harmless commands, among them: any `git push` in a Bash call whose other git command names `production`, for example `git push origin fid-1 && git fetch origin production`; any `gh api` write with a field equal to `production`, for example `-f environment=production` on deployments; a read that names the branch and whose `-X GET` comes later in the line, with or without a field, or is written in lowercase; and every write under `branches/production/`, branch protection included.
- Infra deploys (`deploy-infra.yml`) stay on `main`.

## Consequences

- App code merged to `main` reaches fidant.se only when a maintainer promotes it. Until then fidant.se runs an older commit than `main`. A promotion ships every commit on `main` up to the one promoted.
- The infra and the app can drift apart. `deploy-infra.yml` still deploys on every push to `main` that touches the files it checks out, while the app waits for a promotion. So a pull request that changes both goes live in two steps, and so does an infra change that relies on an app change not yet promoted:
  - A merge that replaces the app box puts the new box live at once, and the new box builds the older `production` branch with the new box config.
  - An infra change that reads a new app route meets the old release until the promotion. 0015's "Fidant relay status unreachable" is one such alarm.
  - Removing a relay deletes its box at the merge, while the app keeps its key in the relay list until the promotion.
  - A maintainer merges a pull request that replaces the app box or removes a relay, and agents don't (AGENTS.md, Merging). The maintainer promotes `main`'s tip just before the merge and the merge right after it lands. The second promotion then carries only that pull request, unless another merge lands in between.
  - Whoever merges any other pull request asks a maintainer to promote that merge right after it lands, when its infra relies on app code not yet promoted or when infra already live relies on its app changes. One example is a replaced relay's new public key in `apps/server/relays.json`.
  - A runbook step that waits for a release waits for the promotion, not the merge.
- A rollback or an app fix in an emergency waits for a maintainer. The revert merges to `main`. The maintainer promotes `main`'s tip, or the revert's own merge commit, which ships the least. Either ships everything merged before the revert. These work at once, without a promotion: 0015's "Turn the relay list off at once", and the "Emergency stop" for coturn in 0007 (the app box) and 0013 (the relay box). None of them stops the app itself from serving a release.
- `main`'s ruleset also allows rebase merges. A rebase merge puts each commit of the pull request's branch on `main`'s first-parent history, so the box accepts those intermediate commits too, and they never passed CI on their own. Agents never rebase-merge (AGENTS.md, Merging), and a maintainer must not either. A maintainer could enforce that by turning off rebase merges in `main`'s ruleset.
- The branch only moves forward, so a commit pushed to `production` that isn't on `main`'s first-parent history is refused, and every later promotion must be a commit that contains it. AGENTS.md, Releasing, says how.
- A check that fails is tried again every minute, and logs `could not check <sha> against main` each time, until it passes or refuses. Meanwhile the box keeps serving its current release.
- The rulesets let an agent's push to `production` through, because agents push with a maintainer's credentials. AGENTS.md's rule bars agents from promoting, and the hook stops only the commands it blocks (see Decision). Whatever moves the branch, the box still builds only commits on `main`'s first-parent history.
- A new app box builds `production` from its first boot, so the branch must exist before a box boots (AGENTS.md, `FidantApp`).
- Going back to deploying from `main` means pointing `fidant-deploy` (`apps/infra/box/user-data.sh`) back at `main` and updating the app box's name pinned in `apps/infra/src/stacks.test.ts`. That replaces the app box once, and the new box builds `main`'s tip at once, so every commit not yet promoted ships without a maintainer.

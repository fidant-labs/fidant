# Sigill

Secure file transfer. Files are encrypted in the sender's browser, and no infrastructure (our servers, hosts, relays, email) can read file content, except through a peer-to-peer link that Fidant emails (see Invariants). Verified transfers add BankID identity, a signed receipt, and a tamper-evident audit log.

Planning lives in Linear: workspace `sigill`, team `SIG`, issue keys like `SIG-21`.

## Commands

- `pnpm install`: installs dependencies and the git hooks.
- `pnpm start`: builds the web client and serves it over HTTPS on `PORT` (default 8443), on all network interfaces, and prints the addresses to open. The first start creates a self-signed certificate in `.certs/` (or in `CERT_DIR` if set); browsers show a warning once. It sends no mail unless `MAIL_SMTP_URL`, `MAIL_FROM` and `PUBLIC_ORIGIN` are all set, so by default the send page offers no email field (`README.md` shows how to try emailed links with Mailpit). It hands out no STUN or TURN servers unless `TURN_URLS` and `TURN_SECRET_FILE` are set, `RELAYS_FILE` names a relay list in the format of `apps/server/relays.json` (`docs/decisions/0015-relay-switch.md`), or `STUN_URLS` names `stun:` URLs, which it hands out with no credentials while neither of the other two applies (`docs/decisions/0023-hosting-off-the-box.md`). A relay list that isn't empty replaces `TURN_URLS`, and the server keeps the master its relay secrets come from in `RELAY_MASTER_FILE`, which it creates 0600 when missing. Set `RELAY_MASTER_FILE` with `RELAYS_FILE`: its default, `/var/lib/sigill/relay-master`, is in a directory that only the app box and the networks suite's box have. Where `/var/lib/sigill` exists and `RELAYS_FILE` is unset, the server reads the committed `apps/server/relays.json`. On macOS, a browser on another laptop needs Local Network access (System Settings → Privacy & Security → Local Network) or the page "can't be reached", even though `curl` works.
- `pnpm check`: lint, typecheck, unit tests and build across the workspace. Run it before every commit. The pre-push hook runs it too.
- `pnpm format`: fixes formatting and safe lint issues.
- `pnpm e2e`: builds the web client, starts the local stack (coturn, Mailpit and the server, whose relay list names two relays on that coturn, the first with a wrong secret) and runs the Playwright suite in `apps/e2e` (Chromium). It is not part of `pnpm check`. Browser traffic and server logs are written to `apps/e2e/observations/`. Playwright traces and reports stay local and are never uploaded. One-time setup: `pnpm --filter @sigill/e2e exec playwright install chromium`. `SIGILL_E2E_BROWSER=firefox` or `=webkit` runs it in that engine instead, one engine per run, after `pnpm --filter @sigill/e2e exec playwright install firefox webkit` (`apps/e2e/README.md`). `.github/workflows/nightly.yml` runs Chromium, with the 1 GB and 5 GB files that `SIGILL_E2E_LARGE=1` turns on, Firefox and WebKit every night, on `workflow_dispatch` and on a pull request that changes that file, each as a user that can only reach loopback, and fails when that user sends anything else, or, on the Chromium and Firefox legs, makes a name lookup to a loopback port 53 (`docs/decisions/0027-nightly-large-files-and-egress-block.md`). A run that isn't for a pull request and fails or is cancelled comments on the open issue titled "Nightly failed" that the Actions bot opened, or opens one. Every other pull request runs Chromium only.
- `pnpm e2e:networks`: builds the web client and runs only `apps/e2e/tests/networks.spec.ts`, transfers between browsers in Docker networks behind simulated NAT routers, with the server, coturn, a relay box set up by `apps/infra/relay/install.sh` and the signaling image (`apps/server/Dockerfile`) behind an nginx stand-in for the load balancer in containers too. It needs no host Chromium or coturn. `pnpm e2e` never runs it. See `apps/e2e/README.md`.
- `pnpm lighthouse`: builds the web client, starts the server on port 8444 and scores the public pages with Lighthouse (`apps/web/lighthouserc.json`), failing below each category's minimum. It needs a local Chrome and is not part of `pnpm check`; CI's `lighthouse` job is disabled until SIG-135 makes its scores stable. Reports go to `apps/web/.lighthouseci/` and are never uploaded.
- `pnpm --filter @sigill/infra cdk deploy FidantDns --profile fidant-dns` and `pnpm --filter @sigill/infra cdk deploy FidantApp --profile fidant-poc`: deploy the AWS infrastructure in `apps/infra`, all of it in eu-north-1 except `FidantDnssec`, `FidantPagesCerts` and `FidantPages`, which are in us-east-1. Sign in first with `aws sso login --sso-session fidant`. The app reads the two account IDs from the untracked `apps/infra/.env` (see `.env.example`) and gives each profile only its own account's stacks, so a deploy under the wrong profile finds no stack. Bootstrap each account once with `pnpm --filter @sigill/infra cdk bootstrap --profile <profile>`, which bootstraps every region the app has stacks in for that account (eu-north-1 and us-east-1 for both). A deploy that adds a stack in a new region needs that bootstrap first. `fidant-poc` is already bootstrapped in us-east-1: a bootstrap run on 2026-11-25 reported no changes.
  - The first deploy has a fixed order, because the DNS records need the box's address from another account: deploy `FidantApp` with the `fidant-poc` profile, copy its `PublicIp` output into `boxAddress` in `apps/infra/src/config.ts`, deploy `FidantDns` with the `fidant-dns` profile and commit the value. At the registrar (a separate AWS account), fidant.se, fidant.eu and fidant.org point at the name servers that `FidantDns` outputs. `FidantDns` has termination protection, so `cdk destroy` refuses it until the protection is turned off.
  - A push to `main` that touches one of the files the workflow checks out, or the workflow itself, deploys `FidantDns`, `FidantDnssec`, `FidantApp`, `FidantSignal` and `FidantPages` through `.github/workflows/deploy-infra.yml`. The workflow checks out only `apps/infra/`, the root `package.json`, `pnpm-workspace.yaml`, `pnpm-lock.yaml` and `.node-version`. It runs in the GitHub environment `production`, which deploys only from `main` (deployment branches set to selected branches, exactly `main`, and no tag rules) and holds the account IDs as the secrets `FIDANT_DNS_ACCOUNT` and `FIDANT_POC_ACCOUNT`. The environment must exist with that policy and both secrets before anything else: a workflow run creates a missing `production` with no branch policy, and any branch could then get a token the role trusts. It signs in to each account through GitHub OIDC as the role `fidant-ci-deploy`, which trusts only that environment's token and may only assume the CDK bootstrap roles. Its runs wait in one queue with those of `release.yml`, so an infra deploy can wait behind releases and other infra runs (`docs/decisions/0023-hosting-off-the-box.md`, which says how long and what the queue does not order, among them a deploy by hand).
  - `FidantCi` holds that role and the OIDC provider, one per account. In `fidant-poc` it also holds `fidant-release`, the role that `.github/workflows/release.yml` signs in as. That role trusts only the token of the GitHub environment `app`, whose only deployment branch is `production` and which holds `FIDANT_POC_ACCOUNT` as its secret, and it has exactly the rights that `docs/decisions/0023-hosting-off-the-box.md` lists. CI never deploys `FidantCi`. Deploy it by hand once per account, only after the `production` environment is set up (in `fidant-poc`, the `app` environment too), and again after changing `apps/infra/src/ci.ts`, a `config.ts` name it reads or its props in `app.ts`: `pnpm --filter @sigill/infra cdk deploy FidantCi --profile fidant-dns`, then the same with `--profile fidant-poc`. Before the `fidant-poc` deploy, `gh api repos/sigill-labs/sigill/environments/app --jq '.deployment_branch_policy | [.protected_branches, .custom_branch_policies] | @tsv'` must print `false` and `true` separated by a tab, and `gh api repos/sigill-labs/sigill/environments/app/deployment-branch-policies --jq '.branch_policies[] | [.name, .type] | @tsv'` must print exactly one line, `production` and `branch` separated by a tab. After a change to the release role alone, `pnpm --filter @sigill/infra cdk diff FidantCi --profile fidant-dns` must print `There were no differences`, and only the `fidant-poc` deploy is needed. The first change that triggers the workflow merges only after that. If one account's deploy job fails at sign-in with "The web identity token provided could not be validated", `FidantCi` is missing from that account; deploy it again there.
  - `FidantPagesCerts` (us-east-1) and `FidantSignalCerts` (eu-north-1), both in `fidant-poc`, hold the certificates for the CDN's three distributions and for the signaling load balancer (`docs/decisions/0023-hosting-off-the-box.md`). CI never deploys them. Their validation records are `certificateRecords` in `apps/infra/src/config.ts`, which `FidantDns` publishes in each name's zone, and their IDs are `certificateIds`. Deploy them by hand once, and again after a change to a `config.ts` name they read or their props in `app.ts`: `pnpm --filter @sigill/infra cdk deploy FidantPagesCerts FidantSignalCerts --profile fidant-poc --concurrency 2`. Each stack waits in `CREATE_IN_PROGRESS` until its records resolve, and CloudFormation keeps waiting after Ctrl-C once both stacks show that status. Read the records and the certificates' IDs, which prints no account ID: `for region in us-east-1 eu-north-1; do for arn in $(aws acm list-certificates --region "$region" --profile fidant-poc --certificate-statuses PENDING_VALIDATION --query 'CertificateSummaryList[].CertificateArn' --output text); do echo "$region uuid ${arn##*/}"; aws acm describe-certificate --region "$region" --profile fidant-poc --certificate-arn "$arn" --query 'Certificate.DomainValidationOptions[].[DomainName,ResourceRecord.Name,ResourceRecord.Value]' --output text; done; done`. It must print 4 `uuid` lines and 7 lines of a name, its record's name and its record's value; run it again while a line shows `None`. ACM stops trying 72 hours after it makes a record, and the certificate then needs a new request, so the pull request with the records must merge early enough that its `deploy-infra.yml` run, which can wait behind releases and other infra runs, ends within 72 hours of the deploy.
  - `FidantDnssec` signs the zones, but resolvers only check the signatures once the registry has a DS record for the domain. The DS records are set by hand at the registrar's AWS account (its CLI profile name is in SIG-80): read the key's public key from `aws route53 get-dnssec --hosted-zone-id <id> --profile fidant-dns`, then `aws route53domains associate-delegation-signer-to-domain --region us-east-1 --profile <registrar-profile>` per domain, fidant.org first, and check each with DNSViz before the next. Add DS records only once the old hosted zones in the registrar's AWS account are gone (SIG-80), the topic's off-domain subscriber is confirmed, and at least two days (the zones' NS TTL) after signing went live, so no resolver still holds unsigned answers or the old delegation. A DS record that doesn't match the zone's key makes the domain unreachable for validating resolvers, which most are. So while a DS record is published, never replace the KMS key or a key-signing key (a test pins their logical IDs) and never delete `FidantDnssec` (it has termination protection). To roll back, remove the DS record first (`disassociate-delegation-signer-from-domain`), wait for the registry's DS TTL to pass, and only then turn signing off.
  - `FidantApp` (account `fidant-poc`) is the Lightsail box that serves the app at fidant.se and redirects the other five names to it. HAProxy holds 443 and hands each connection on by SNI, without decrypting it: `turn.fidant.se` to coturn, everything else to Caddy on 8444 with the PROXY protocol, so the app still sees client addresses. Caddy comes from Caddy's own apt repository, because Ubuntu's is too old for the PROXY protocol. Caddy serves HTTPS with Let's Encrypt certificates, so fidant.se must point at the box before Caddy can get one; if it pointed elsewhere when the box booted, `systemctl restart caddy` through Lightsail's browser SSH makes Caddy retry at once instead of after a growing delay. The box deploys the app itself: every minute it reads the `production` branch (see Releasing) from GitHub and builds a new commit into `/opt/sigill/releases/<sha>`. It builds only a commit on `main`'s first-parent history, which it checks right after cloning, before checkout and `pnpm install`. It refuses any other commit with the journal line `refused <sha>: not on main`. When the check itself fails, it logs `could not check <sha> against main` and tries again on the next run. It switches `/opt/sigill/current` to the new release only if the build succeeds, and switches back if the server does not answer within about a minute. A commit that is refused, or whose build or start fails, is marked in `/opt/sigill/failed-<sha>` and not retried; delete that file to retry. The box's instance name carries a hash of its user data, so changing `apps/infra/box/user-data.sh` or anything `apps/infra/src/user-data.ts` renders into it replaces the box, among them `apps/infra/box/turnserver.conf`, `boxAddress`, `mailFrom`, `primaryDomain`, `zoneNames`, `.node-version` and the pnpm version. The test "the app box keeps its name" in `apps/infra/src/stacks.test.ts` pins that name, so such a change must update the pin. The static IP moves to the new box at once, and the site is down for the 5–10 minutes it needs to install, get certificates and build. A merge that replaces the box replaces it when its infra run's `FidantApp` job deploys, and that run waits in the queue behind every release and infra run ahead of it, which can include the release that the promotion just before the merge started (`docs/decisions/0023-hosting-off-the-box.md`). The box reads `production` itself, outside the queue, so the old box builds any promotion made before the replacement with the old box config, and the new box builds `production`'s tip when it boots, with the new one. So a maintainer promotes `main`'s tip just before merging it and that merge right after it lands. The second promotion then carries only that pull request, unless another merge lands in between (see Merging). The `production` branch must exist before a box boots; without it the box logs `no production branch` every minute and serves nothing. Create it once with `git fetch origin && git push origin refs/remotes/origin/main:refs/heads/production`. Then `git ls-remote origin refs/heads/production` must print one line: the sha that `git rev-parse refs/remotes/origin/main` prints, a tab and `refs/heads/production`. Lightsail runs the script through `/bin/sh`, so it must stay POSIX sh. `pnpm e2e:networks` checks the box's logging in an Ubuntu container, not on the Lightsail image, so after the box is replaced run `systemd-analyze cat-config systemd/journald.conf` once through browser SSH and check that `ForwardToSyslog=no`, `MaxRetentionSec=29day` and `MaxFileSec=1day` are the last values.
  - The box also runs coturn, the STUN and TURN relay at `turn.fidant.se` (`docs/decisions/0007-turn-relay.md` and, for TURN over TLS on 443, `docs/decisions/0010-turn-tls-443.md`; both have runbooks). The app offers it only when it has no relay list (`docs/decisions/0015-relay-switch.md`), until SIG-264 takes it off the box. coturn's TLS uses Caddy's certificate for `turn.fidant.se`, which `sigill-turn-cert.timer` copies to `/etc/coturn/` within 5 minutes of each change, so TLS comes up within minutes of Caddy getting it after first boot. First boot generates its secret into `/etc/sigill/turn-secret` and gives the app `TURN_URLS` and the secret only if coturn started; otherwise the app has no relay to fall back on. App deploys don't restart coturn. Emergency stop through browser SSH: `systemctl stop coturn`. The relay cost cap (`docs/decisions/0021-relay-cost-cap.md`) closes this coturn's 3478 and its UDP relay range but not its TLS listener, because the box keeps 443 for the site and HAProxy hands `turn.fidant.se` on. While the app has a relay list it mints no credentials for this coturn. If the relay list is turned off while the cap is active, it mints them again (0015) and relayed traffic can still pass over TLS, which the cap can't stop and the emergency stop does (SIG-162). The relay keeps no log; a temporary log, only to fix a fault or stop abuse, stays on for at most 7 days. The budget alert "Fidant POC monthly cost" can't be created by CloudFormation in eu-north-1 (SIG-90).
  - `FidantApp` also holds the Stockholm relay box `fidant-relay-sto-<hash>`, a second Lightsail Micro whose user data is `apps/infra/relay/install.sh` with its inputs (`docs/decisions/0013-relay-service.md`, which has the runbook). Its static IP is retained, and its address is the `RelayStoIp` output. Its public key is in `/etc/fidant-relay/relay.pub`, and the install prints it at the end of `/var/log/cloud-init-output.log`. It carries the site's relayed transfers while the app has a relay list. The app trusts its public key in `apps/server/relays.json`, hands it its secret sealed to that key at `/relay-secret/sto`, and offers it once a TURN allocation on it has succeeded, until two checks in a row fail (`docs/decisions/0015-relay-switch.md`, which has the runbooks for the relay status, turning the relay list off, new relay secrets, a leaked relay key and the live cap check). The app derives every relay's secret from a master in `/var/lib/sigill/relay-master` on the app box, which anything running as `sigill` can read; never print it, only test that it exists. Its instance name carries a hash of its user data, so a change to `install.sh` or to its inputs replaces it. The new box makes a new key pair, and it gets no secret until a pull request commits its new public key to `apps/server/relays.json` and a maintainer promotes it. Until then the app offers no relay, unless the relay list is turned off (0015). Its secrets are in `/var/lib/fidant-relay/` (`current`, `previous` and the `turndb` database); never print them or `relay.key`, only test that they exist.
  - `FidantSignal` (account `fidant-poc`, eu-north-1) runs signaling behind the load balancer that `sto.signal.fidant.se` names, beside the box and unused until the cutover (`docs/decisions/0023-hosting-off-the-box.md`): a VPC with two public subnets and no NAT gateway, the load balancer `fidant-signal`, the cluster `fidant` with the service `fidant-signal`, which runs one Fargate task of the image tagged `live` in the registry `fidant-signal`, and the relay master in Secrets Manager. It joins the CDK app only once `certificateIds.signal.sto` in `apps/infra/src/config.ts` holds its certificate's ID. Its first deploy needs an image tagged `live`, or the service never settles and the deploy job waits up to its 60-minute timeout, so the pull request that first adds it merges only when `aws ecr describe-images --repository-name fidant-signal --image-ids imageTag=live --region eu-north-1 --profile fidant-poc --query 'length(imageDetails)' --output text` prints `1`. A deploy of `FidantSignal` and a release both start deployments of the one service, and the queue the two workflows share holds their runs one at a time (see Merging for what it leaves out). No person reads or prints the relay master in Secrets Manager; only the task's start-up role reads it. It exists when ``aws secretsmanager describe-secret --secret-id "$(aws cloudformation describe-stack-resources --stack-name FidantSignal --region eu-north-1 --profile fidant-poc --query "StackResources[?ResourceType=='AWS::SecretsManager::Secret'].PhysicalResourceId" --output text)" --region eu-north-1 --profile fidant-poc --query 'ARN != `null`' --output text`` prints `True`, which shows no value and no account ID. Raising `relayMasterGeneration` in `config.ts` makes a new relay master and restarts the task. After a release or a deploy, the task runs the image `live` names when `aws ecs describe-tasks --cluster fidant --tasks "$(aws ecs list-tasks --cluster fidant --service-name fidant-signal --desired-status RUNNING --region eu-north-1 --profile fidant-poc --query 'taskArns[0]' --output text)" --region eu-north-1 --profile fidant-poc --query 'tasks[0].containers[0].imageDigest' --output text` prints the same digest as `aws ecr describe-images --repository-name fidant-signal --image-ids imageTag=live --region eu-north-1 --profile fidant-poc --query 'imageDetails[0].imageDigest' --output text`.
  - `FidantPages` (account `fidant-poc`, us-east-1) will serve the pages from the cutover and is unused until then (`docs/decisions/0023-hosting-off-the-box.md`): the private, versioned bucket `fidant-pages-<account>`, which only the fidant.se distribution reads and only `fidant-release` writes, and three CloudFront distributions, one per zone with its `www`. Each has its own function built from `apps/infra/edge/site.js`, its own web ACL with no rules and no sampled requests, and its own free flat-rate plan; fidant.se's also passes `/relay-secret/<id>` uncached to `sto.signal.fidant.se`, through its own function as viewer request, which guards any URI that contains `/relay-secret/` once its escapes are decoded and its backslashes read as slashes, because AWS gives no order for the steps with which CloudFront normalises a path before it matches a behaviour (`docs/decisions/0023-hosting-off-the-box.md` cites the page). The guard passes a request on only when the URI as sent is exactly `/relay-secret/<id>` with an id of the server's rule `^[a-z][a-z0-9]{1,15}$`, and answers the function's empty 404 with the three headers and HSTS, instead of what the page rule would give it, to everything else the guard sees, so a path elsewhere that merely contains `/relay-secret/`, such as `/how/relay-secret/x`, gets that empty 404, not the 404 page. It joins the CDK app only once `certificateIds.pages` in `apps/infra/src/config.ts` holds all three certificates' IDs. If the account can't have the free plan, its first create rolls back and deletes the bucket, which CloudFormation keeps after any later delete or replacement (`RetainExceptOnCreate`, https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-attribute-deletionpolicy.html). Every later `cdk deploy FidantPages` (each infra push, and 0023's pay-as-you-go follow-up itself) deletes a rolled-back stack and creates it again (aws-cdk 2.1149.0's `isCreationFailure`, not verified on a live stack); a release waits in the queue while such a run goes on (`docs/decisions/0023-hosting-off-the-box.md`, "Deploys, and who can change what visitors run"), and its upload step ends red when its check, at the start of the step, finds `FidantPages` mid-operation or missing, which covers a stack operation that a cancelled or timed-out infra run leaves running. Until FidantPages exists, before the first create and after a rolled-back create until the follow-up's create, every release run ends red at "Upload the web client", and the success of its "Push the image, move live and redeploy" step is what to check then. The bucket is kept after a stack delete and its name is fixed, so recreating the stack needs the kept bucket imported first with `cdk import` (https://docs.aws.amazon.com/cdk/v2/guide/ref-cli-cmd-import.html, https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/resource-import.html). The function goes live when its pull request merges. A new public page adds its path to `PAGES` in `apps/infra/edge/site.js` in the same pull request, which `apps/e2e/src/pages.test.ts` checks, and until a maintainer promotes the release that has the page, the CDN answers its path with S3's bare 404. Read the distributions' names, which hold no account ID, with `aws cloudformation describe-stacks --stack-name FidantPages --region us-east-1 --profile fidant-poc --query 'Stacks[0].Outputs[].[OutputKey,OutputValue]' --output text`, which prints three lines, each an output name ending in `DistributionName`, a tab and a name ending in `.cloudfront.net`.
  - The app sends its email through Amazon SES in eu-north-1 as `noreply@notify.fidant.se` (`docs/decisions/0012-email-recipients.md`). `FidantApp` holds the SES domain identity, its default configuration set (no tracking, TLS required, no account suppression list, bounces and complaints to an SNS topic nobody subscribes to) and the IAM user `fidant-mail`, which may only send from that identity. Alarms named "Fidant SES reputation ..." fire when the account's bounce rate reaches 2 % or its complaint rate 0.05 %, below the 5 % and 0.1 % at which AWS reviews the account (https://docs.aws.amazon.com/ses/latest/dg/reputationdashboardmessages.html). Each emails budget-alert@fidant.se through the relay alarms' topic and invokes the Lambda `MailPause`, which turns sending off for the configuration set `fidant-mail` (`ses:PutConfigurationSetSendingOptions`, which takes the configuration set's ARN: https://docs.aws.amazon.com/service-authorization/latest/reference/list_amazonsimpleemailservicev2.html; AWS's own version of this pattern: https://docs.aws.amazon.com/ses/latest/dg/monitoring-sender-reputation-pausing-configuration-set.html). Every send then fails, and the send page says the email was not sent. Nothing turns sending back on by itself. CDK never sets the configuration set's `SendingOptions`, but whether a CloudFormation update to `MailConfig` turns sending back on is untested (SIG-222), so run the sending check below after any deploy that changes `MailConfig`. CDK never creates the user's access key. The key, the SMTP user name and the SMTP password never go in the repo, CloudFormation, a deploy log or Linear. Mail is off on a new box: the app gets its mail settings only from `/etc/systemd/system/sigill.service.d/mail.conf`, and the SMTP password only through `LoadCredential=` from `/etc/sigill/mail-password` (0600 root). `sigill-credential` writes or removes both together, because a drop-in that names a missing file stops the app. Any other credential placed on the box goes the same way.
    - Turn mail on, also after the box is replaced, only when all of these hold. The app server reads the mail settings (SIG-107). SES shows `notify.fidant.se` as verified: `FidantDns` must publish the identity's three DKIM CNAMEs, copied by hand from the `Dkim1..3` outputs into `apps/infra/src/config.ts`, and SES must see them within 72 hours of `FidantApp` first creating the identity. `FidantDns` must also publish the MAIL FROM records for `bounce.notify.fidant.se` (MX `10 feedback-smtp.eu-north-1.amazonses.com` and TXT `v=spf1 include:amazonses.com -all`), so bounces reach SES and SPF aligns; these are fixed SES values, not outputs, and need a records change in `apps/infra/src/dns.ts`. SES shows the identity's Bounce and Complaint notification topics set to the feedback topic and feedback forwarding off (`aws ses get-identity-notification-attributes --identities notify.fidant.se --profile fidant-poc --region eu-north-1`). `FidantApp` sets them in the deploy that first adds these settings and again when one of their values changes, not on every deploy, so never change the identity's notification topics or forwarding by hand, except to set back exactly these values as below. SES accepts them while the identity's verification is still pending. SES itself turns feedback forwarding back on and removes a topic it fails to publish to (deleted, or SES lost permission to publish), so run that check again after any change to the feedback topic, its policy or the identity, and after any SES email saying it re-enabled feedback forwarding. If the check shows anything else, turn mail off and set the three values back by hand to what `FidantApp` sets. Get the feedback topic's ARN with `aws sns list-topics --query "Topics[?contains(TopicArn, 'MailFeedback')].TopicArn" --output text --profile fidant-poc --region eu-north-1`. Run `aws ses set-identity-notification-topic --identity notify.fidant.se --notification-type Bounce --sns-topic <that ARN> --profile fidant-poc --region eu-north-1`, the same with `Complaint`, and `aws ses set-identity-feedback-forwarding-enabled --identity notify.fidant.se --no-forwarding-enabled --profile fidant-poc --region eu-north-1`. Run the check, and turn mail on only after it passes. SES has granted production access, or every address you test with is verified in SES: the sandbox refuses all other recipients while the send page still offers email. Then list the user's keys with `aws iam list-access-keys --user-name fidant-mail --profile fidant-poc` and delete any old one with `aws iam delete-access-key --user-name fidant-mail --access-key-id <id> --profile fidant-poc` (a user has at most two). Then, from an up-to-date checkout of `main`, run `aws iam create-access-key --user-name fidant-mail --profile fidant-poc --output json | node apps/infra/src/smtp-password.ts`, which prints the SMTP user name and password and never the secret access key. `aws` creates the key even when `node` fails, for example because the checkout predates the script, and its secret is then lost: if it prints no password, delete the key it made before trying again. In Lightsail's browser SSH run `sudo sigill-credential mail on` and paste the two when asked. It restarts the app, which drops transfers in progress and email-bound links. The send page then shows the email field. Never use the SES console's "Create SMTP credentials": it creates a user that can send from any identity.
    - Turn mail off: `sudo sigill-credential mail off` through browser SSH. Never delete `/etc/sigill/mail-password` by hand: the next deploy restarts the app, and it would not start. Without the box, `aws iam update-access-key --user-name fidant-mail --access-key-id <id> --status Inactive --profile fidant-poc` makes every send fail at once, though the page still offers email. `aws sesv2 put-configuration-set-sending-options --configuration-set-name fidant-mail --no-sending-enabled --profile fidant-poc --region eu-north-1` does the same for every sender, and is what `MailPause` does.
    - Check sending: `aws sesv2 get-configuration-set --configuration-set-name fidant-mail --query SendingOptions.SendingEnabled --output text --profile fidant-poc --region eu-north-1` prints `True` while SES sends and `False` while it is paused. If a "Fidant SES reputation" alarm emailed and the check still prints `True`, `MailPause` failed: pause by hand as above.
    - Resume sending after a pause, only once the cause is understood: `aws sesv2 put-configuration-set-sending-options --configuration-set-name fidant-mail --sending-enabled --profile fidant-poc --region eu-north-1`, then the check, which must print `True`. An alarm acts only when its state changes (https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/AlarmThatSendsEmail.html), so an alarm still in ALARM would not pause again: set each "Fidant SES reputation" alarm in ALARM back with `aws cloudwatch set-alarm-state --alarm-name "<name>" --state-value OK --state-reason resumed --profile fidant-poc --region eu-north-1`. If the rate is still over its threshold, the next datapoint fires the alarm and pauses sending again.

- gitleaks (`brew install gitleaks`). The pre-commit hook fails without it.
- openssl, for the local certificate. macOS and Linux ship with it.
- Git 2.39 or later, for `git patch-id --verbatim` in the review gate.

- AWS CLI v2, only for deploying `apps/infra`. Its SSO profiles (`fidant-mgmt`, `fidant-dns`, `fidant-poc`) are in SIG-54.

## Layout

- `apps/*`: things we run or ship. `apps/web` is the Preact client, built by Vite into `apps/web/dist`. `apps/server` is the Node process that serves it and relays signaling messages between browsers over a WebSocket at `/signal`. It also checks the relays in `apps/server/relays.json` every minute and hands each relay its sealed secret at `/relay-secret/<id>`. `apps/e2e` is the end-to-end harness (see `docs/decisions/0001-e2e-tests-and-leak-model.md`).
- `apps/infra` (`@sigill/infra`): the AWS CDK app. `FidantDns` (account `fidant-dns`) holds the hosted zones for fidant.se, fidant.eu and fidant.org and every record in them; all six site names and `turn.fidant.se` point at the box's static IP, copied by hand into `boxAddress` in `apps/infra/src/config.ts`; `sto.relay.fidant.se` points at the relay box's static IP, copied by hand into `relayAddresses` in the same file. Changing `relayAddresses` replaces no box. Removing a relay removes it from `relayAddresses` as well as `relays`, and its retained static IP is released by hand only after its name no longer resolves, because a released address that DNS still points at lets whoever gets it pass Let's Encrypt's HTTP challenge for our name. `sto.signal.fidant.se` is a CNAME, with a 60-second lifetime, for the signaling load balancer's DNS name, copied by hand from `FidantSignal`'s `LoadBalancerDnsName` output into `signalTargets` in the same file. `FidantApp` (account `fidant-poc`) is the app box, the Stockholm relay box, the SES identity the app sends mail through and the registry `fidant-signal` for the signaling image; the app box's first-boot script is `apps/infra/box/user-data.sh`. `FidantDnssec` (account `fidant-dns`, us-east-1, where Route 53 requires DNSSEC keys) holds the KMS key that signs the three zones, a key-signing key and signing for each zone, and alarms named "Fidant DNSSEC ..." that email budget-alert@fidant.se and an off-domain address subscribed to the topic by hand (not in the repo), since a DNSSEC failure can make budget-alert@fidant.se unreachable; that subscription must be confirmed before the first DS record and added again if the topic is ever replaced; it finds the zones by the IDs copied by hand into `hostedZoneIds` in `apps/infra/src/config.ts`. `FidantPagesCerts` and `FidantSignalCerts` (account `fidant-poc`) hold the AWS certificates for the CDN and the signaling load balancer. `FidantCi` (both accounts) holds the role that CI deploys with, and in `fidant-poc` the role that `release.yml` releases with. `FidantPages` (account `fidant-poc`, us-east-1) is the pages bucket and the three distributions that will serve the six site names, with the edge function `apps/infra/edge/site.js`. Every other stack is in eu-north-1, except `FidantPagesCerts` in us-east-1. Its box-script and AWS facts are in `apps/infra/AGENTS.md`.
- `apps/infra/relay/install.sh`: the standalone relay install script. Run as root with `RELAY_ID`, `RELAY_NAME` and `APP_URL` set, it makes any Ubuntu 24.04 server a Fidant relay: coturn with its own Let's Encrypt certificate, a host firewall, a key pair, and timers that fetch the relay's secret from `APP_URL`, keep `external-ip` in step with `RELAY_NAME` and get the first certificate. It is POSIX sh and depends on nothing AWS-specific. A relay gets its secret only once its public key is in `apps/server/relays.json`.
- `packages/*`: code used by more than one app. Create a package only when a second consumer exists.
- `packages/protocol` (`@sigill/protocol`): signaling message types, parsers and limits shared by the server and the web client.
- `docs/decisions/`: decision records. Its README has the format and what a runbook check or command must do.
- `docs/how-fidant-works.md`: how Fidant moves a file and why no infrastructure can read it, except through a peer-to-peer link that Fidant emails. The source of truth for the security model and data flow (see Invariants).
- Workspace packages export TypeScript source directly (`"exports": { ".": "./src/index.ts" }`). Internal packages have no build step.
- Every package with TypeScript has a `typecheck` script (`tsc --noEmit -p .`) and, if it has tests, a `test` script. The root scripts run them recursively.

## Conventions

- Node runs `.ts` files directly through type stripping. Use only erasable TypeScript syntax (no `enum`, `namespace` or constructor parameter properties). Relative imports include the `.ts` extension.
- `apps/web` is Preact 11 with Vite, not React or Next.js. React guidance applies only where Preact has the same API. Check the Preact docs (https://preactjs.com) before using an API, and import from `preact` and `preact/hooks`. Skip rules about Next.js, React Server Components, `React.cache`, `<Activity>` and server actions. `startTransition`, `useTransition` and `useDeferredValue` from `preact/compat` run updates synchronously with no deferral (`isPending` is always `false`), so rules that rely on them for responsiveness or pending UI don't apply. Don't add SWR, `better-all` or `lru-cache` without a separate decision.
- Unit tests use `node:test` and sit next to the code as `*.test.ts`.
- End-to-end specs live in `apps/e2e/tests/` and import `test` from `apps/e2e/src/fixtures.ts` and open browsers with its `actor` fixture, so traffic is recorded.
- Box tests in `apps/e2e/tests/networks.spec.ts` share containers across the run: change one only inside the `try` whose `finally` undoes it, compare its times with its own `date +%s` or allow for drift against the host's `Date.now()`, and when a test finds no secret in a log, also prove the checked output reached that log.
- Dependencies: `pnpm add --filter <package> <dep>`. pnpm is strict, so each package declares everything it imports.
- Workspace packages: add one as a dependency with `pnpm add --filter <consumer> --workspace <package>`, which links and saves `workspace:*`. Without `--workspace`, pnpm can resolve the name from the public npm registry.
- Commits: conventional commits, subject line only, imperative, under 72 characters, for example `feat: add signaling server`.
- Branches: `sig-<number>-<short-slug>` after the Linear issue. One pull request per issue. `main` is protected: changes land only through pull requests with green CI.
- Pull request titles start with the Linear issue key (`SIG-21: ...`) so Linear links them.
- Keep the Linear issue's status current while working: assign it and set "In Progress" when work starts, link the pull request when it opens, and set "Done" when it merges.

## Merging

- An agent may merge a pull request when the required `check` passed and the latest review by `github-actions[bot]` on the pull request's current head commit is an approval. The approval counts only with a successful `Claude review` run on that same commit, because any workflow in this repository can post a review as `github-actions[bot]`.
- The `Claude review` workflow sees only `main` and the pull request's diff. A record, invariant or setting that another unmerged pull request adds reads to it as a broken reference.
- Pull requests that touch `.github/**`, `AGENTS.md`, `CLAUDE.md`, `.claude/**`, `.agents/**`, `.mcp.json`, `skills-lock.json`, `apps/server/relays.json` or the files the infra deploy checks out (`apps/infra/**`, the root `package.json`, `pnpm-workspace.yaml`, `pnpm-lock.yaml` and `.node-version`) also need an approval from the `maintainers` team. Authors cannot approve their own pull requests, so the other developer approves. The `sensitive-paths` ruleset enforces this, and repository admins can bypass it.
- Agents never approve pull requests, never merge with `--admin` or any other rule bypass, and never change rulesets, teams or repository settings.
- Agents merge pull requests only into `main`, and only with `gh pr merge --merge`, never squash or rebase. A rebase merge puts the branch's intermediate commits on `main`'s first-parent history, and the box then accepts them (`docs/decisions/0020-deploy-from-production.md`). Every merge to `main` so far has been a merge commit.
- Agents never merge a pull request that changes the app box's name pinned in the test "the app box keeps its name" in `apps/infra/src/stacks.test.ts`, which means it replaces the box, or that removes a relay. A maintainer merges it, and promotes `main`'s tip just before and that merge right after it lands. The `FidantApp` bullet under Commands says which box builds which promotion. Until the second promotion, the app box keeps handing new secrets to the removed relay's key, and a new app box that boots before it runs the older `production` release under the new box config. A removed relay changes `STUN_URLS`, so that merge also updates `FidantSignal`.
- The queue that `release.yml` and `deploy-infra.yml` share holds their runs one at a time, in no guaranteed order, and does not wait for the AWS work they start (`docs/decisions/0023-hosting-off-the-box.md` says what else it leaves out). A release that would move `live` on a running signaling service ends red, without moving it, when it can't read `FidantSignal`'s status or that status ends in `_IN_PROGRESS`. That covers a `FidantSignal` update that a cancelled or timed-out `deploy-infra.yml` run leaves running; the newest release run, the one for `production`'s tip, is re-run once the stack has settled. Any other status, one that ends in `_FAILED` included, lets the release go on. A job of a `deploy-infra.yml` run, whatever its conclusion, is re-run only while that run is the newest one, because a re-run keeps its commit and an older template would undo a later merge.
- Whoever merges any other pull request asks a maintainer to promote that merge right after it lands, when its infra relies on app code not yet promoted or when infra already live relies on its app changes. One example is a replaced relay's new public key in `apps/server/relays.json`.
- Agents never push to the `production` branch or promote a release. A hook, `.claude/scripts/production-guard.sh`, blocks the common commands that would. `docs/decisions/0020-deploy-from-production.md` lists what it blocks and what it misses. It is a guardrail only, because agents push with a maintainer's credentials.

## Releasing

- fidant.se runs the `production` branch (`docs/decisions/0020-deploy-from-production.md`). App code merged to `main` reaches fidant.se only when a maintainer promotes it.
- Two rulesets, set by hand in GitHub and not in this repository, protect the `production` branch: only the `maintainers` team may update it, and they refuse deleting it or moving it other than forward, with no bypass. Repository admins can still change the rulesets. The GitHub environment `production` is unrelated to the `production` branch; infra deploys (`deploy-infra.yml`) run from `main`.
- The box builds only a commit on `main`'s first-parent history, and refuses any other. To promote, from a clone of the repository:
  - Run `git fetch origin`, then list the candidates with `git log --first-parent --oneline refs/remotes/origin/production..refs/remotes/origin/main`.
  - Resolve the commit once and print its full sha: `sha=$(git rev-parse refs/remotes/origin/main) && echo "$sha"`. To promote an older commit, use `sha=$(git rev-parse <commit>) && echo "$sha"` with a commit that the `--first-parent` listing shows.
  - Read what will ship, from the release the box serves, which can be older than `production` after a refused or failed promotion. In Lightsail's browser SSH on the app box, `readlink /opt/sigill/current` prints `/opt/sigill/releases/<served sha>`. Then run `git diff --stat <served sha> "$sha"` and `git diff <served sha> "$sha"`. If `readlink` prints nothing, the box serves no release yet, and everything at `$sha` ships. The diff shows every change to the checkout that the box installs and builds, as `sigill`, which can read the relay master: `pnpm install --frozen-lockfile`, then the root `pnpm build` over every workspace package. Dependencies show only as lockfile changes.
  - Push it: `git push origin "$sha":refs/heads/production`. The full refs are deliberate: a tag named `origin/main` or `production` would otherwise shadow the branch or make the push fail.
  - Check it through Lightsail's browser SSH on the app box. Within about 3 minutes, or about 15 minutes after a box replacement, `readlink /opt/sigill/current` must print `/opt/sigill/releases/<sha>`, with the sha that `echo "$sha"` printed. The box switches to the release before its health check and switches back if that fails, so wait until the run has ended, when `systemctl is-active sigill-deploy` prints `inactive` or `failed` instead of `activating`. Either can follow a failed run, so the next two checks decide. Then `test -e /opt/sigill/failed-<sha> && echo failed || echo ok` must print `ok`, and `readlink /opt/sigill/current` must still print the release. If either doesn't, `journalctl -u sigill-deploy --since -20min` shows why, for example `refused <sha>: not on main`, `could not check <sha> against main` or a build error.
  - The push also starts `.github/workflows/release.yml`, which releases the signaling image to the registry and then uploads the web client to the pages bucket (`docs/decisions/0023-hosting-off-the-box.md`). The box uses neither, so a failed run leaves fidant.se as it is, and the run's log in the repository's Actions tab shows why it failed. Check it once the run has ended: `gh run list --workflow release.yml --branch production --limit 1 --json headSha,conclusion --jq '.[0] | [.headSha,.conclusion] | @tsv'` must print the sha that `echo "$sha"` printed, a tab and `success`. While the run waits or is still going, nothing follows the tab. It waits while any earlier release or infra deploy runs, because both workflows share one queue. Until FidantPages exists (see the FidantPages bullet) the run ends red at "Upload the web client" and its "Push the image, move live and redeploy" step is what to check.
  - A run also ends in `success` when it skips the image and its upload succeeds: after a release whose new task failed its health check, the image for those inputs carries the tag `failed-<key>`, and every later release with the same inputs deploys no image, still uploads the web client unless the upload step ends it red, and shows the warning `the server image for these inputs failed before and is not deployed` on the run's page in the Actions tab, with the key in the tag it names. To try that image again, delete the tag with your own sign-in, using that key: `aws ecr batch-delete-image --repository-name fidant-signal --image-ids imageTag=failed-<key> --query 'imageIds[].imageTag' --output text --region eu-north-1 --profile fidant-poc` must print `failed-<key>`. Then re-run all jobs of the newest release run, the one for the commit that `production` is at (an older run refuses, because it would move `live` back to an older image), or promote a later commit; that release tries the image again.
  - A run whose log shows `could not move live back to <previous>: it still names <new>` moved `live` to an image the service was never confirmed to run and could not move it back, so a release with those inputs ends without deploying until `live` moves. Move it back with your own sign-in, using the two digests the error names: `[ "$(aws ecr batch-get-image --repository-name fidant-signal --image-ids imageTag=live --query 'images[0].imageId.imageDigest' --output text --region eu-north-1 --profile fidant-poc)" = <new> ] && m=$(aws ecr batch-get-image --repository-name fidant-signal --image-ids imageDigest=<previous> --query 'images[0].imageManifest' --output text --region eu-north-1 --profile fidant-poc) && t=$(aws ecr batch-get-image --repository-name fidant-signal --image-ids imageDigest=<previous> --query 'images[0].imageManifestMediaType' --output text --region eu-north-1 --profile fidant-poc) && aws ecr put-image --repository-name fidant-signal --image-tag live --image-manifest "$m" --image-manifest-media-type "$t" --query 'image.imageId.imageDigest' --output text --region eu-north-1 --profile fidant-poc` must print `<previous>`. It prints nothing and moves nothing when `live` no longer names `<new>`, for example after a later release moved it; then leave `live` and the runs as they are. When it printed `<previous>`, check it: `aws ecr batch-get-image --repository-name fidant-signal --image-ids imageTag=live --query 'images[0].imageId.imageDigest' --output text --region eu-north-1 --profile fidant-poc` must print `<previous>`. If it does, re-run all jobs of the newest release run, the one for the commit that `production` is at.
- The `production` branch only moves forward, so a rollback is a revert pull request on `main`, then a promotion. Promote `main`'s tip, or the revert's own merge commit, which ships the least. Either ships everything merged before the revert. 0020's Consequences list the stops that work at once, without a promotion.
- A commit pushed to `production` that isn't on `main`'s first-parent history is refused by the box. `release.yml` refuses it only while the commit's own copy of the workflow keeps the check, a gap that SIG-285 closes (`docs/decisions/0023-hosting-off-the-box.md`). The branch only moves forward, so every later promotion must be a commit that contains it:
  - If `main` already contains it, for example as an intermediate commit of a merged pull request, promote `main`'s tip.
  - Otherwise it first lands on `main` through a pull request whose branch contains it, merged with a merge commit, because a squash or rebase merge makes new commits that don't contain it. Then promote `main`'s tip.

## Invariants

- Never send file content, file names, file metadata or keys to the server or any other infrastructure, and never log them. Two deliberate exceptions: the BankID receipt text names the file, and when Fidant emails a peer-to-peer link, the link's key and the name the sender typed for themselves pass through our server and our mail service (see `docs/decisions/0012-email-recipients.md`).
- Keys live only in the URL fragment or in browser memory. Two exceptions: the server-held half of a verified transfer's split key, which the server stores and releases only after the receipt is signed (see `docs/decisions/0001-e2e-tests-and-leak-model.md`), and the key in a peer-to-peer link that Fidant emails, which our server holds in memory only until it refuses the registering message, its one send attempt ends, or the sender's socket closes before the attempt starts, and which passes through our mail service (see `docs/decisions/0012-email-recipients.md`).
- What counts as a leak, concretely, is defined in `docs/decisions/0001-e2e-tests-and-leak-model.md`, read with the records that amend it: 0002, 0003, 0004, 0012 and 0027 in `docs/decisions/`.
- `docs/how-fidant-works.md` describes the code on `main`. A change that touches security or data flow updates it in the same pull request: keys, encryption, the link format, frames, signaling messages, connection paths and the relay, what the server or relay sees, keeps or logs, limits, HTTP headers, or a new mode of transfer. The same pull request updates the web text that explains it: the `technical` text in `apps/web/src/i18n/en.ts` and `sv.ts`, and `/how`, `/privacy`, `/security` and the landing page wherever the change makes them untrue. An exception makes untrue every absolute that covers it, such as "never", "nobody", "us included" or "every", in that text, in any `AGENTS.md`, in `.claude/` and in `docs/` outside accepted decision records, which a new record amends instead.
- "Every path and its traces" in `docs/how-fidant-works.md` is the audit baseline: every way a file or a shared secret moves and the traces each part keeps, shown to readers by the `/how/traces` explorer. A change to a path, a trace, a signaling message or a log field updates it, and the explorer's text, in the same pull request. The `Claude review` workflow checks every path on each pull request, and `packages/protocol/src/transfer-paths.test.ts` fails when a message, log event or named file is missing from it.
- This repository is public. Never commit secrets, real personal data or customer data. The pre-commit hook runs gitleaks, and the `check` job in CI scans the pushed commits again. That scan runs after the push, when a secret is already public, so a hit there means rotate the secret first, then remove it. GitHub push protection is on, but blocks only known token formats. Both scans skip a line marked `gitleaks:allow`.
- The project must run fully local for tests and demos, with no internet. Add infrastructure (database, storage, relay) only when a feature needs it.

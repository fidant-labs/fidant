# Infra

Facts for the scripts that run on a box and for what CDK deploys. The deploy steps and the box test conventions are in the root `AGENTS.md`, runbooks are there and in the decision records, and what a runbook check or command must do is in `docs/decisions/README.md`.

## Box scripts

- A box runs its user data once, at first boot, and the scripts that user data writes stay as written. `src/user-data.ts` renders each box's user data, and the box's instance name carries a hash of that text, so a change to the text it renders for a box replaces that box. Its inputs include `box/` for the app box, `relay/install.sh` for every relay box, and values it puts in, such as `boxAddress`, `.node-version` and the relay's name. A fix found after merge costs a box replacement, and a new relay box has a new key pair.
- Lightsail runs user data through `/bin/sh`, which is dash on Ubuntu. The scripts it writes name their shell on the `#!` line.
- `set -e` stops a script at a failing command, but not everywhere, and `grep` fails with exit 1 when nothing matches. Among the places a failure doesn't stop it: an `if`, `while` or `until` condition, before `&&` or `||`, after `!`, and any but the last command of a pipeline. The same holds for the whole body of a function called in a condition, before `&&` or `||`, or after `!` (`if f`, `f || exit 1`), and for a failing `$( )` in another command's arguments (`echo "$(false)"`) or in `local x=$(false)` or `export x=$(false)`, though `x=$(false)` alone stops it. dash has no `set -o pipefail`; bash has it.
- dash's `$(( ))` reads a leading zero as octal (`010` is 8, `08` is an error) and clamps a literal past 9223372036854775807 to that number (so does `$(($n))`, while `$((n))` stops the script with `Illegal number`). A computed result past the limit is not clamped and can come out negative, zero or positive: `$((9223372036854775807+1))` is -9223372036854775808, `$((4611686018427387904*4))` is 0 and `$((9223372036854775807*3))` is 9223372036854775805. `[ "$n" -gt 1 ]` reads base 10, but fails with exit 2 on an empty value, a non-number or a number past that limit, and in an `if` condition the failure takes the `else` branch. A value that matches `0` or `[1-9][0-9]*` with at most 18 digits is read as its base-10 value in both.
- A daemon reads its config when it starts or reloads, which a crash restart or another script can cause at any moment. A file truncated and rewritten in place can be read half written. coturn with no authentication option in its config allows anonymous relaying, so a `turnserver.conf` cut off before `use-auth-secret` is an open relay.
- `mv` within one file system replaces a file atomically, so a file written in full under another name and then moved over the target is never read half written. `mktemp` creates its file 0600 root:root, so the mode and group the daemon needs are set before the `mv`.
- Two runs of one script can overlap: a timer and a manual run, or two installs. A fixed temp name such as `x.new` is shared between them, and one run can move the other's half-written file into place. A name from `mktemp` in the target's directory (`mktemp /etc/turnserver.conf.XXXXXX`) is unique to its run.

## systemd

- `systemctl is-active` succeeds only for an active, reloading or refreshing unit. While a unit is `activating` it prints `activating` and exits 3, and a oneshot service is `activating` for its whole run.
- `try-restart` restarts a unit that is active, activating, reloading or refreshing, and does nothing to one that is inactive, failed or deactivating.
- The default start limit is 5 starts in 10 s, and every start counts: manual, `Restart=` and `try-restart`. Past it, every start fails until the 10 s have passed or `systemctl reset-failed` clears the count, and the unit stays failed until something starts it again, which `try-restart` never does. The relay's coturn has a drop-in with `StartLimitIntervalSec=0`; the app box's coturn keeps the default.
- A timer fires up to its `AccuracySec=` late, 1 minute by default.
- `systemctl start` on a service whose start is still running joins that run. Nothing serializes two direct runs of the same script.
- `systemd-run --pipe` connects the unit's stdin, stdout and stderr to the caller, so its output never reaches the journal.

## Names and certificates

- `getent` follows `/etc/nsswitch.conf`, which on Ubuntu is `hosts: files dns`. A name in `/etc/hosts` is answered from there and never reaches DNS, and some installers add `127.0.1.1 <hostname>`.
- Let's Encrypt counts failed validations per DNS name per account: at most 5 an hour, and after 1,152 in a row it pauses that name for the account until someone unpauses it through the link in the error. A validation fails while the name doesn't resolve to the box, so every certificate request made before DNS points there spends both.

## Secrets

- Every local user can read an external command's arguments in `ps` and `/proc/<pid>/cmdline`. A builtin such as `printf`, `read` or `[` starts no new program, so its arguments don't show there, though its error message can print them (`[ abc -gt 1 ]` prints `Illegal number: abc`). `set -x` prints each command after expansion, assignments and builtins included: `s=$(cat file)` traces as `+ s=<secret>`, and `printf '%s\n' "$s"` and `[ "$s" = x ]` show the value too. A function, a subshell, a `$( )` or a sourced file inherits `-x`; a script run as its own process (`sh file`, `/path/file`) does not. In user data that trace goes to `/var/log/cloud-init-output.log`, and a unit's stdout and stderr go to the journal by default. `fidant-relay-apply-secret` and `fidant-credential` hold a secret in shell variables without `-x`, put it in no external command's arguments, and hand it on only through a file or a pipe. `sudo` logs each full command line, arguments included, to the journal, which the box keeps 29 days, and an interactive shell saves command lines to its history.
- A filter removes a secret only inside the command that prints it. Once printed, the secret is in the terminal's scrollback or the journal.

## AWS

- The tests in `src/` synthesize templates or run code against fakes; none calls AWS. A claim about what AWS accepts (which IAM actions take a resource ARN, what SES needs before it accepts a setting, what the SES sandbox allows, how Lambda loads a module) rests on an AWS doc or an observed run. The pull request body cites it for the maintainers. The CI reviewer sees only `main` and the diff, so it sees the citation only where the diff adds it, for example in the record or `AGENTS.md` text the claim goes into. An agent asks the user before a run that needs an AWS account or a live box (the app box or a relay box).
- A CloudWatch alarm runs its actions only when its state changes, and `set-alarm-state` holds only until the next evaluation (https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/AlarmThatSendsEmail.html). A Lambda alarm action is invoked asynchronously by the principal `lambda.alarms.cloudwatch.amazonaws.com` (https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/alarms-and-actions-Lambda.html). The Node.js Lambda runtimes include the AWS SDK for JavaScript v3, so inline code can `require("@aws-sdk/client-sesv2")` (https://docs.aws.amazon.com/lambda/latest/dg/lambda-nodejs.html).
- ACM issues only where CAA allows one of `amazon.com`, `amazontrust.com`, `awstrust.com` or `amazonaws.com`, so each apex's CAA record names `amazon.com` beside Caddy's two authorities. ACM checks CAA after it validates the name, and a certificate refused for CAA then needs a new request (https://docs.aws.amazon.com/acm/latest/userguide/setup-caa.html, https://docs.aws.amazon.com/acm/latest/userguide/troubleshooting-caa.html).
- CloudFormation writes a certificate's DNS validation records only for a Route 53 zone in the stack's own account. For a name hosted elsewhere, the stack stays in `CREATE_IN_PROGRESS` until someone adds the records (https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-certificatemanager-certificate.html, https://docs.aws.amazon.com/cdk/api/v2/docs/aws-cdk-lib.aws_certificatemanager-readme.html). The docs don't name the case of a Route 53 zone in another account, as fidant-dns's zones are for fidant-poc's stacks. An observed run settles it: on 2026-11-26 the certificate stacks waited in `CREATE_IN_PROGRESS` until `FidantDns` published the records in fidant-dns's zones, then completed about 3 minutes later. So the certificates live in stacks of their own that CI never deploys, and no stack imports from them. ACM gives each name one record per account, the same in every region, so it stays valid for a replacement or a copy elsewhere. ACM stops trying 72 hours after it makes the record, and the certificate then needs a new request (https://docs.aws.amazon.com/acm/latest/userguide/dns-validation.html). The records are read from `aws acm describe-certificate`, under `DomainValidationOptions[].ResourceRecord` (https://docs.aws.amazon.com/acm/latest/APIReference/API_DomainValidation.html). ACM refuses an empty list of alternative names (https://docs.aws.amazon.com/acm/latest/APIReference/API_RequestCertificate.html).
- IAM matches a GitHub token's claims as condition keys: `token.actions.githubusercontent.com:aud` and `:sub`, and `:job_workflow_ref`, which names the workflow file that defines the job, the called file for a job in a reusable workflow (https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_iam-condition-keys.html#condition-keys-wif). `fidant-ci-deploy` trusts only the `production` environment's `sub`. `fidant-release` trusts only the `app` environment's, and only from a job of `release-jobs.yml` on `main`: its `job_workflow_ref` must be `fidant-labs/fidant/.github/workflows/release-jobs.yml@refs/heads/main`. That claim names the owner and repository, not their IDs. A probe run on 2026-11-27 printed `fidant-labs/fidant/.github/workflows/<file>@refs/heads/<branch>` both for a plain job and for a job in a workflow it called. Unlike `sub`, which carries the IDs, the claim follows the name, and a rename can free the old owner or repository name for anyone to claim. Whoever then holds it can serve `release-jobs.yml` at the old path, and a job of ours that calls that path runs their file in our `app` environment, with our `sub` and a claim that matches a trust still naming the old path. So the trust never names the old path once the rename is done: before the rename, `FidantCi` is deployed trusting the new path alone, which refuses every release. `release.yml`, which calls `release-jobs.yml`, moves to the new path, and releases sign in again, only once the rename is done, because until then someone else can hold the new name, and our job would run their file with a claim the trust matches. That move is the first merge after the rename: until `production` holds it, a push to `production` can run whatever a new holder of the old name serves, in our `app` environment, which hands it the account ID; a re-run of all jobs of a release whose commit doesn't hold the move can, even after that, because it keeps that run's own `release.yml`, which names the old path, and resolves `@main` again at re-run time, so such runs are never re-run. `apps/e2e/src/release.test.ts` pins the caller's path as a literal, so the trust (`releaseWorkflow` in `config.ts`) and the caller move in separate merges. Trusting the old and new names side by side, as 0028 did for `sub`, never applies to this claim. A role's `MaxSessionDuration` (1 hour by default, at most 12) limits how long a session from `AssumeRoleWithWebIdentity` can last, and the call's `DurationSeconds` can't exceed it, so `fidant-release` allows 2 hours and the release job asks for 7200 seconds, more than its waits take (https://docs.aws.amazon.com/STS/latest/APIReference/API_AssumeRoleWithWebIdentity.html, https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_update-role-settings.html). A `StringEquals` condition on a key that the request doesn't carry doesn't match, so an Allow on it fails closed and a Deny on it doesn't apply. Some operators, such as `ForAllValues`, can match a key that isn't there (https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_elements_condition.html).
- Pushing to one ECR repository takes `ecr:BatchCheckLayerAvailability`, `ecr:InitiateLayerUpload`, `ecr:UploadLayerPart`, `ecr:CompleteLayerUpload`, `ecr:PutImage` and `ecr:BatchGetImage` on the repository's ARN, and `ecr:GetAuthorizationToken`, which has no resource type, on `*` (https://docs.aws.amazon.com/AmazonECR/latest/userguide/image-push-iam.html, https://docs.aws.amazon.com/service-authorization/latest/reference/list_amazonelasticcontainerregistry.html).
- `ecs:UpdateService` and `ecs:DescribeServices` take the service's ARN, `arn:aws:ecs:<region>:<account>:service/<cluster>/<service>`. UpdateService's condition keys include `ecs:enable-execute-command` and `ecs:task-definition`, and none for the desired count, so IAM can't keep the release role from changing it (https://docs.aws.amazon.com/service-authorization/latest/reference/list_amazonelasticcontainerservice.html). The release role denies UpdateService when `ecs:enable-execute-command` is `true`, so a release that leaves exec unset passes whether or not the request carries the key, and one that turns exec on is refused.
- `s3:ResourceAccount` matches the account that owns the bucket, so an Allow on a bucket name with it can't reach a bucket of that name in another account. `s3:PutObject` supports it (https://docs.aws.amazon.com/AmazonS3/latest/userguide/amazon-s3-policy-keys.html, https://docs.aws.amazon.com/service-authorization/latest/reference/list_amazons3.html).
- `cloudformation:DescribeStacks` takes the stack's ARN, `arn:aws:cloudformation:<region>:<account>:stack/<name>/<id>`, as an optional resource type, and describes every stack only together with `cloudformation:ListStacks`, which has no resource type. So the release role's grants on `stack/FidantSignal/*` and `stack/FidantPages/*` list no stack (https://docs.aws.amazon.com/service-authorization/latest/reference/list_awscloudformation.html, read 2026-11-26). The page doesn't say that a call naming a stack is checked against that ARN; the first release that reaches each check once its stack exists settles it, and a refusal ends that step red before `live` moves or before any upload.
- ECR moves a tag without a pull or push: `batch-get-image` reads the image's manifest, and `put-image` with that manifest and `--image-tag` puts the tag on it (https://docs.aws.amazon.com/AmazonECR/latest/userguide/image-retag.html). A manifest without a `mediaType` field also needs `--image-manifest-media-type`. `put-image` fails with `ImageAlreadyExistsException` when the image already has that tag, and with `ImageTagAlreadyExistsException` when an immutable tag already names another image (https://docs.aws.amazon.com/AmazonECR/latest/APIReference/API_PutImage.html). A repository with `IMMUTABLE_WITH_EXCLUSION` keeps every tag immutable except the ones its exclusion filters match, `live` for `fidant-signal` (https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-ecr-repository.html, https://docs.aws.amazon.com/AmazonECR/latest/userguide/image-tag-mutability.html). `batch-delete-image` with an `imageTag` removes only that tag, and deletes the image only when it was the last tag (https://docs.aws.amazon.com/AmazonECR/latest/APIReference/API_BatchDeleteImage.html). The mutability page says `ImageTagAlreadyExistsException` answers any push of a tag already in the repository, so the release job also takes it as done when that tag already names the image it tags. That page speaks only of overwriting a tag and doesn't say whether immutability lets a tag be deleted; the first hand delete of a `v2-failed-<key>` tag settles it. The release role has no `ecr:BatchDeleteImage`, so only a maintainer's own sign-in deletes that tag.
- No ECR page documents an exception in lifecycle rules for an image a service runs, and ECS starts a service's later tasks by the digest its deployment resolved (https://docs.aws.amazon.com/AmazonECS/latest/developerguide/deployment-type-ecs.html#deployment-container-image-stability), so a rule that expires a tagged image can leave a replacement task with nothing to pull. `fidant-signal`'s one rule expires only untagged images, 7 days after their push, and moving `live` leaves the old image its commit and inputs tags. An image is expired by exactly one or zero rules, a rule can't expire an image that a higher-priority rule's tag selection matches, and images expire up to 24 hours after they meet the rule (https://docs.aws.amazon.com/AmazonECR/latest/userguide/LifecyclePolicies.html).
- `FidantSignal` names its two zones, `eu-north-1a` and `eu-north-1b`. CDK otherwise looks a stack's zones up in the account at synth time, as missing context (https://docs.aws.amazon.com/cdk/api/v2/docs/aws-cdk-lib.Stack.html), and `Fn::GetAZs` lists only zones with a default subnet, in an order that can change (https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/intrinsic-function-reference-getavailabilityzones.html), which would move a subnet.
- An application load balancer's health check speaks HTTP unless `HealthCheckProtocol` says otherwise, whatever the target group's protocol (https://docs.aws.amazon.com/elasticloadbalancing/latest/APIReference/API_CreateTargetGroup.html). It doesn't validate a target's certificate, so the server's self-signed one works (https://docs.aws.amazon.com/elasticloadbalancing/latest/application/load-balancer-target-groups.html#target-group-routing-configuration). A newly registered target must pass one health check to count as healthy, `HealthyThresholdCount` applies to an unhealthy target turning healthy, and a target group whose registered targets are all unhealthy routes requests to all of them (https://docs.aws.amazon.com/elasticloadbalancing/latest/application/target-group-health-checks.html, read 2026-11-26).
- `routing.http.xff_header_processing.mode` defaults to `append`, which adds the client's address as the last `X-Forwarded-For` entry; `preserve` passes on the client's own header and `remove` drops it. `routing.http.xff_client_port.enabled` defaults to `false`; with it on, the entry is `address:port`, which the server's address rule ignores (https://docs.aws.amazon.com/elasticloadbalancing/latest/application/application-load-balancers.html#load-balancer-attributes, https://docs.aws.amazon.com/elasticloadbalancing/latest/application/x-forwarded-headers.html). CDK writes the client port attribute only when it is `true`, so `FidantSignal` sets it itself.
- The load balancer closes a connection that sends or receives no data for its idle timeout, 1 to 4000 seconds and 60 by default; a TCP keep-alive doesn't count. AWS recommends a target idle timeout longer than the load balancer's, or the load balancer can send a request on a connection the target just closed and answer 502 (https://docs.aws.amazon.com/elasticloadbalancing/latest/application/edit-load-balancer-attributes.html#connection-idle-timeout). `FidantSignal`'s is 120 seconds, and the container's `HTTP_KEEP_ALIVE_MS` is 125000.
- Access logs, connection logs and health check logs are off by default (https://docs.aws.amazon.com/elasticloadbalancing/latest/application/load-balancer-access-logs.html, https://docs.aws.amazon.com/elasticloadbalancing/latest/application/load-balancer-connection-logs.html, https://docs.aws.amazon.com/elasticloadbalancing/latest/application/load-balancer-health-check-logs.html). CloudWatch Logs can also receive all three as vended logs, which CloudFormation sets up with `AWS::Logs::DeliverySource` (https://docs.aws.amazon.com/elasticloadbalancing/latest/application/load-balancer-cloudwatch-logs.html, https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-logs-deliverysource.html). `stacks.test.ts` checks both paths stay off.
- An HTTPS listener made through CloudFormation or CDK gets `ELBSecurityPolicy-2016-08`, which allows TLS 1.0, unless it names a policy. `FidantSignal` names `ELBSecurityPolicy-TLS13-1-2-Res-PQ-2025-09`, which AWS recommends: TLS 1.2 and 1.3, with post-quantum key exchange for clients that offer it and classical for the rest. The policy for connections to targets follows the listener's (https://docs.aws.amazon.com/elasticloadbalancing/latest/application/describe-ssl-policies.html).
- ECS counts `maximumPercent` over tasks that are RUNNING or PENDING and `minimumHealthyPercent` over RUNNING ones (https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_DeploymentConfiguration.html). CDK's `FargateService` defaults them to 50 and 200, unlike ECS (https://docs.aws.amazon.com/cdk/api/v2/docs/aws-cdk-lib.aws_ecs.FargateServiceProps.html), so `FidantSignal` sets 0 and 100: the old task stops before a new one starts. No page says whether a task that is still draining holds the slot. The target group waits 300 seconds by default before it lets a deregistered target go, unless the target has no connections (https://docs.aws.amazon.com/elasticloadbalancing/latest/application/edit-target-group-attributes.html#deregistration-delay); `FidantSignal`'s waits 5, since open WebSockets count and clients reconnect. ECS deregisters a task from its target group in the DEACTIVATING state and sends SIGTERM only in STOPPING, so that drain runs before the server knows it is stopping, and a client may see the load balancer's close (1006) instead of the server's 4012 (https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task-lifecycle-explanation.html). The container's `stopTimeout` is 5 seconds, where Fargate defaults to 30 and accepts 2 to 120 (https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_ContainerDefinition.html).
- With desired count 1, the circuit breaker fails a deployment after 3 failed tasks and rolls back to the most recent COMPLETED deployment. With none, it launches nothing and the deployment stalls (https://docs.aws.amazon.com/AmazonECS/latest/developerguide/deployment-circuit-breaker.html). A task that never reaches RUNNING, for example because its image is missing, is retried with growing delays, up to 27 minutes apart (https://docs.aws.amazon.com/AmazonECS/latest/developerguide/service-throttle-logic.html). No page read says how long CloudFormation waits on a service that never settles, so a first create with nothing tagged `live`, or with a task that can't start, is taken to hold the deploy job up to its 60-minute timeout.
- ECS turns an image tag into a digest at a deployment's first task and starts that deployment's later tasks by the digest; a forced deployment resolves the tag again (https://docs.aws.amazon.com/AmazonECS/latest/developerguide/deployment-type-ecs.html#deployment-container-image-stability). A rollback reuses the last successful service revision, which records the digest (https://docs.aws.amazon.com/AmazonECS/latest/developerguide/service-revision.html). `FidantSignal` sets `versionConsistency` to enabled, the default.
- A secret reaches the container when it starts, and a new value doesn't reach a running task (https://docs.aws.amazon.com/AmazonECS/latest/developerguide/secrets-envvar-secrets-manager.html). A change to `GenerateSecretString` makes a new version under the same ARN (https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-secretsmanager-secret.html), which changes no task definition. So `relayMasterGeneration` is part of the secret's logical ID: raising it makes a new secret with a new ARN, a new task definition revision and a deployment. What CloudFormation does with the replaced secret, and its recovery window, is unread. The start-up role needs `secretsmanager:GetSecretValue` on the secret, and the containers can't use that role (https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task_execution_IAM_role.html).
- Fargate takes tmpfs mounts since January 2026, so a read-only root can keep one writable directory in memory (https://aws.amazon.com/about-aws/whats-new/2026/01/amazon-ecs-tmpfs-mounts-aws-fargate-managed-instances/, https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task_definition_parameters.html). The mount options list names `uid`, `gid` and `mode` but shows no way to give them a value (https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_Tmpfs.html), and CDK's option type has no such form, so `FidantSignal` writes `uid=1000`, `gid=1000` and `mode=700` as Docker's `--tmpfs` takes them. Docker Desktop makes a bare tmpfs root's, and the image's user `node` can't write there. The first task settles it: ECS refuses the task definition, or the task stops when the entrypoint can't write the master, or it runs. The fallback, an empty bind mount, is owned by root with mode 0755 unless the image has a `VOLUME` line for that path, whose files and owner then carry over (https://docs.aws.amazon.com/AmazonECS/latest/developerguide/bind-mounts.html).
- ECS Exec is off unless a service turns it on, and needs a task role with Session Manager rights and a writable root (https://docs.aws.amazon.com/AmazonECS/latest/developerguide/ecs-exec.html). An exec, like a container health check, would also inherit `RELAY_MASTER`, so the service sets it off and the task has neither.
- A Fargate task pulls its image, fetches its secrets and sends its logs through its own network interface, so a public subnet and a public address replace a NAT gateway (https://docs.aws.amazon.com/AmazonECS/latest/developerguide/fargate-task-networking.html). CDK's `assignPublicIp` defaults to off.
- Log groups take a retention from a fixed list, 14 days among them, and AWS deletes events typically within 72 hours after it (https://docs.aws.amazon.com/AmazonCloudWatchLogs/latest/APIReference/API_PutRetentionPolicy.html). CDK makes `FidantSignal`'s group, so the start-up role needs no `logs:CreateLogGroup` (https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task_definition_parameters.html).
- ECS turns Availability Zone rebalancing on for a new service unless told otherwise. Rebalancing starts a task before it stops one, and can't be used with a `maximumPercent` of 100 (https://docs.aws.amazon.com/AmazonECS/latest/developerguide/service-rebalancing.html), so `FidantSignal` turns it off.
- ECR's `batch-get-image` answers a tag or digest it doesn't find in the response, with a `failures` entry whose code is `ImageNotFound` and no image for it. That isn't one of the call's errors, so the call succeeds (https://docs.aws.amazon.com/AmazonECR/latest/APIReference/API_BatchGetImage.html, https://docs.aws.amazon.com/AmazonECR/latest/APIReference/API_ImageFailure.html).
- ECS's `describe-services` fails with `ClusterNotFoundException` when the cluster doesn't exist, and answers a service the cluster doesn't have with a `failures` entry whose reason is `MISSING` (https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_DescribeServices.html, https://docs.aws.amazon.com/AmazonECS/latest/developerguide/api_failures_messages.html). A deployment's `status` is `PRIMARY`, `ACTIVE` or `INACTIVE`, and its `rolloutState` is `IN_PROGRESS`, then `COMPLETED` once the service reaches a steady state, or `FAILED` when it doesn't and the circuit breaker is on. A FAILED deployment launches no new tasks (https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_Deployment.html). `.github/workflows/release-jobs.yml` relies on these answers.
- CloudFront takes certificates only from us-east-1, web ACLs for CloudFront exist only there, and the flat-rate plans' API is only there (https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-properties-cloudfront-distribution-viewercertificate.html, https://docs.aws.amazon.com/PricingPlanManager/latest/UserGuide/getting-started-pricingplanmanager-api.html), so `FidantPages` and its bucket are in us-east-1.
- An account has at most 3 free flat-rate plans, a quota that can't be raised, and each plan covers one distribution with at most one apex domain. A distribution on a plan must have a WAF web ACL, and a function or web ACL associated with it can be used for no other distribution, so `FidantPages` has one function and one web ACL per distribution, built from the same file. A subscribed distribution can't be deleted until its plan is cancelled; a free plan is cancelled at once. Accounts "using AWS Free Tier" are not eligible, which the docs don't define. Free has CloudFront Functions and 5 cache behaviors, but no access logs, no WAF request logs, and no custom cache, origin request or response headers policies (https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/flat-rate-pricing-plan.html).
- `AWS::PricingPlanManager::Subscription` takes `PlanFamily: CloudFront`, a `PlanTier` and `ResourceArns`, which for CloudFront must hold a distribution's ARN and a web ACL's. Free subscriptions are active at once; a paid tier waits in `PENDING_APPROVAL`, which CloudFormation never approves. A stack update can't change the tier or the usage level. AWS's free example's web ACL has no rules and sets `SampledRequestsEnabled` and `CloudWatchMetricsEnabled` to false (https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-pricingplanmanager-subscription.html).
- A web ACL's `SampledRequestsEnabled` is required, and a sample keeps each request's source address and URI for 3 hours (https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-properties-wafv2-webacl-visibilityconfig.html, https://docs.aws.amazon.com/waf/latest/developerguide/web-acl-testing-view-sample.html). `stacks.test.ts` pins it off on every web ACL, with no rules.
- CloudFront runs no viewer-response function when the origin answers 400 or more, and in a viewer response only `Warning` and `Via` are read-only (https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/edge-function-restrictions-all.html). A function is at most 10 KB, which can't be raised (https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/cloudfront-limits.html). A function's own response goes to the viewer without the cache or the origin (https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/function-code-choose-purpose.html), so it carries its own headers.
- `cloudfront-js-2.0` is ES 5.1 with `const`, `let`, arrow functions, rest parameters, template literals, `async` and `await`, and the methods its page lists, such as `startsWith` and `Array.prototype.includes`. The page lists no `??`, `?.`, spread, destructuring, default parameters, `for...of`, classes, `Set` or `Map`, and `edge.test.ts` refuses them. Functions run in strict mode, and `eval` and `Function` throw (https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/functions-javascript-runtime-20.html). `request.rawQueryString()` returns the query as received, without its `?`, and `undefined` when there is no `?` (https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/general-helper-methods.html). The event's request is the one CloudFront received from the viewer; the page doesn't say what a viewer-response event carries after a viewer-request function changed the URI (https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/functions-event-structure.html).
- A function's regular expressions run under an instruction limit and a match limit that no page read documents. On 2026-11-26 `test-function` stopped `site.js` with `RangeError: Regex execute instruction limit exceeded` on the URI `/` with 2,730 `%41` escapes, and on 512-character URIs of `/` with 170 escapes and `A` or with 511 backslashes, and with `RangeError: Regex match limit exceeded` on `/` with 510 lowercase letters and a hyphen, each with no output. So `site.js` uses no regular expression, and `edge.test.ts` fails when it names a regex method or runs one, and answers a path longer than 128 characters, not counting the query, with its own 414, because with a 256 cap `test-function` measured a compute utilisation of 52 on `/` with 255 backslashes, over the trial's limit of 50.
- Behind origin access control, S3 answers a missing object with 403 unless CloudFront may `s3:ListBucket`, and then with 404. With that right a request that reaches S3 as `/` lists the keys, unless the distribution has a default root object (https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html, https://docs.aws.amazon.com/cdk/api/v2/docs/aws-cdk-lib.aws_cloudfront_origins-readme.html). The default root object may name a key in a folder, such as `pages/index.html`, and must not start with `/` (https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/DefaultRootObject.html). CloudFront keeps an error such as that 404 for 10 seconds by default (https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/HTTPStatusCodes.html).
- The managed `CachingOptimized` policy keeps an object for at least its 1-second minimum, even with `Cache-Control: no-cache`, and `CachingDisabled` (`4135ea2d-6df8-44a3-9df3-4b5a84be39ad`) keeps nothing (https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/using-managed-cache-policies.html). With no origin request policy, CloudFront sends the origin the path and its own headers, `Host` set to the origin's name (https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/controlling-origin-requests.html, https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/RequestAndResponseBehaviorCustomOrigin.html).
- CDK's `Distribution` takes CloudFront's `TLSv1.2_2019` unless a feature flag says otherwise, and `cdk.json` sets none (https://docs.aws.amazon.com/cdk/api/v2/docs/aws-cdk-lib.aws_cloudfront.DistributionProps.html), so `FidantPages` names `TLSv1.2_2021`: TLS 1.2 and 1.3 with only GCM and ChaCha20 ciphers (https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/secure-connections-supported-viewer-protocols-ciphers.html). It also sets IPv6 on and redirects HTTP to HTTPS on every behavior itself. The site names get no AAAA record until the cutover (FID-263).
